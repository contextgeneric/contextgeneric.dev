# CGP v0.7.1 - Grouping components with namespaces and paths

**CGP v0.7.1** has been released, and it comes with major ergonomic improvements to manage CGP components at scale. In this blog post, we will explore the problems with managing CGP components, and how the new namespace feature in CGP v0.7.1 helps solve the problem.

{/* truncate */}

## The challenges of scaling CGP

Up until now, one of main challenges of using CGP is on the boilerplate of using `delegate_components!` to wire CGP providers, especially as the number of CGP components grow within an application. When there are too many entries inside `delegate_components!`, developers quickly get lost on what they should pay attention to, and it gives the impression that the application becomes too complex.

### An example social media web app

To demonstrate the challenge, we will make use of a simple web application as an example. Suppose that we want to build a simple social media web app, we could use CGP to define modular traits to expose simple CRUD capabilities for managing users and posts. A simplified version of the traits would look something like follows:

```rust
#[cgp_component(UserManager)]
pub trait CanManageUser {
    fn create_user(&self, username: &str, email: &Email) -> Result<User, Error>;

    fn get_user(&self, user_id: &UserId) -> Result<User, Error>;

    fn update_user_data(&self, user_id: &UserId, user_data: &UserData) -> Result<(), Error>;
}

#[cgp_component(PostManager)]
pub trait CanManagePost {
    fn create_post(&self, title: &str, content: &str) -> Result<Post, Error>;

    fn get_post(&self, post_id: &PostId) -> Result<Post, Error>;

    fn update_post(&self, post_id: &PostId, content: &str) -> Result<(), Error>;

    fn delete_post(&self, post_id: &PostId) -> Result<(), Error>;
}
```

Our trait definitions are as straightforward as vanilla trait definitions, aside from the use of `#[cgp_component]` to turn them into CGP traits. The main advantage is that we can now define context-generic implementations for the traits. For example, we can implement production-ready providers as follows:

```rust
#[cgp_impl(new PostgresUserManager)]
impl UserManager {
    fn create_user(
        &self,
        #[implicit] database: &PostgresDb,
        username: &str,
        email: &Email,
    ) -> Result<User, Error> {
        // ...
    }

    fn get_user(
        &self,
        #[implicit] database: &PostgresDb,
        user_id: &UserId,
    ) -> Result<User, Error> {
        // ...
    }

    fn update_user_data(
        &self,
        #[implicit] database: &PostgresDb,
        user_id: &UserId,
        user_data: &UserData,
    ) -> Result<(), Error> {
        // ...
    }
}

#[cgp_impl(new PostgresPostManager)]
impl PostManager {
    fn create_post(
        &self,
        #[implicit] database: &PostgresDb,
        title: &str,
        content: &str,
    ) -> Result<Post, Error> {
        // ...
    }

    fn get_post(
        &self,
        #[implicit] database: &PostgresDb,
        post_id: &PostId,
    ) -> Result<Post, Error> {
        // ...
    }

    fn update_post(
        &self,
        #[implicit] database: &PostgresDb,
        post_id: &PostId,
        content: &str,
    ) -> Result<(), Error> {
        // ...
    }

    fn delete_post(
        &self,
        #[implicit] database: &PostgresDb,
        post_id: &PostId,
    ) -> Result<(), Error> {
        // ...
    }
}
```

Our production provider implementations are not coupled with any concrete application context, and CGP allows us to reuse it on any application context that provides the required dependencies, such as the PostgreSQL `database` field.

CGP also enables us to define other context-generic provider implementations for the traits, such as an `SqliteUserManager` and `SqlitePostManager` that implements the queries using SQLite instead of PostgreSQL.

With this minimal settings, the configuration for our production application is straightforward, and can be written as follows:

```rust
#[derive(HasField)]
pub struct ProductionApp {
    pub database: PostgresDb,
}

delegate_and_check_components! {
    ProductionApp {
        UserManagerComponent: PostgresUserManager,
        PostManagerComponent: PostgresPostManager,
    }
}
```

With just two lines of configurations, we have managed to configure our `ProductionApp` to use the `PostgresUserManager` and the `PostgresPostManager` providers that we have defined, without tightly coupling the implementations with the `ProductionApp` context.

### Filtering usernames and post messages

Our base implementation of `PostgresUserManager` and `PostgresPostManager` only have a single dependency to the PostgreSQL database. But as the application grows, the methods may require additional dependencies to implement more features.

For example, we may want to ban certain words in the username, or detect and reject spam messages when creating a post. With the earlier traits, we may implement those functionalities as follows:

```rust
#[cgp_component(UsernameCensor)]
pub trait CanCensorUsername {
    fn username_is_censored(&self, username: &str) -> Probability;
}

#[cgp_component(SpamMessageDetector)]
pub trait CanDetectSpamMessage {
    fn message_is_spam(&self, message: &str) -> Probability;
}

#[cgp_impl(new PostgresUserManager)]
#[uses(CanCensorUsername)]
impl UserManager {
    fn create_user(
        &self,
        #[implicit] database: &PostgresDb,
        username: &str,
        email: &Email,
    ) -> Result<User, Error> {
        if self.username_is_censored(username) > Probability::new(0.8) {
            return Err(Error::InvalidUsername)
        }

        // ...
    }

    // ...
}

#[cgp_impl(new PostgresPostManager)]
#[uses(CanDetectSpamMessage)]
impl PostManager {
    fn create_post(
        &self,
        #[implicit] database: &PostgresDb,
        title: &str,
        content: &str,
    ) -> Result<Post, Error> {
        if self.message_is_spam(content) > Probability::new(0.8) {
            return Err(Error::InvalidMessage)
        }

        // ...
    }

    // ...
}
```

In the above example, we introduce two new CGP traits, `UsernameCensor` and `SpamMessageDetector`, to be used by `PostgresUserManager` and `PostgresPostManager`. The providers make use of the probability scores returned by the filters to determine whether to reject the creation of a user or post.

In production, the implementation of features like spam filters may employ sophisticated setup, such as using AI or a cloud service provider. But in testing environments, we may want to make use of simplified setup to test the other parts of the application more quickly. With CGP, we can do so by defining two separate contexts such as follows:

```rust
pub struct ProductionApp {
    pub database: PostgresDb,
    // ...
}

delegate_components! {
    ProductionApp {
        UserManagerComponent: PostgresUserManager,
        PostManagerComponent: PostgresPostManager,
        UsernameCensorComponent: AiUserCensor,
        SpamMessageDetectorComponent: AiSpamMessageDetector,
    }
}

pub struct TestApp {
    pub database: PostgresDb,
    // ...
}

delegate_components! {
    ProductionApp {
        UserManagerComponent: PostgresUserManager,
        PostManagerComponent: PostgresPostManager,
        UsernameCensorComponent: DummyUserCensor,
        SpamMessageDetectorComponent: DummySpamMessageDetector,
    }
}
```

In the example above, we have a `ProductionApp` that is used in production, and a `TestApp` that is used for testing. Both `ProductionApp` and `TestApp` make use of the same PostgreSQL database backend, and thus they reuse the same `PostgresUserManager` and `PostgresPostManager` providers. But `ProductionApp` uses providers that make use of AI to detect spam and censored usernames, while `TestApp` uses dummy implementation that performs detection with simple string pattern matching.

As we can see, CGP makes it easy to organically extend the dependency tree of an application context. However, with the transitive dependencies, we now have 4 items listed in 2 contexts, resulting in 8 wiring configuration entries.

### Fine grained traits

If we look carefully at the implementation of `PostgresUserManager`, we can notice that the trait `CanCensorUsername` is not really needed by `get_user` and `update_user_data`. Similarly, in `PostgresPostManager`, the trait `CanDetectSpamMessage` is not needed by `get_post`, `update_post`, and `delete_post`.

In practice, the accumulation of dependencies like `CanDetectSpamMessage` can quickly pile up in trait implementations, especially when the number of trait methods increases. The long list of dependencies can make it harder to maintain and test the implementations.

As the application grows, pressure will increase on how to better organize which method belongs to which trait. For example, we may need to decide whether a `get_user_profile_picture` method should belong to the `UserManager` trait. Furthermore, when a method involves multiple domains, such as `get_user_posts`, it is not clear whether they should be placed in `UserManager` or `PostManager`.

In more advanced use cases, we may also want to make use of CGP to isolate capabilities that can be used in a piece of code. For example, since user deletion is very destructive, we may not want to expose a `delete_user` method to all code that have access to `UserManager`.

One of the simple but powerful design patterns that is enabled by CGP is that we can break down monolithic trait definitions like `UserManager` into *fine-grained traits* that each contains only one or a handful of items. For example:

```rust
#[cgp_component(UserCreator)]
pub trait CanCreateUser {
    fn create_user(&self, username: &str, email: &Email) -> Result<User, Error>;
}

#[cgp_component(UserGetter)]
pub trait CanGetUser {
    fn get_user(&self, user_id: &UserId) -> Result<User, Error>;
}

#[cgp_component(UserUpdater)]
pub trait CanUpdateUser {
    fn update_user_data(&self, user_id: &UserId, user_data: &UserData) -> Result<(), Error>;
}
```

With the fine grained traits, it becomes much easier for us to isolate the dependencies and only expose them to implementations that really need them. For example, the `CanCensorUsername` consumer trait can now be imported in the `UserCreator` implementation:

```rust
#[cgp_impl(new CreateUserWithPostgres)]
#[uses(CanCensorUsername)]
impl UserCreator {
    fn create_user(
        &self,
        #[implicit] database: &PostgresDb,
        username: &str,
        email: &Email,
    ) -> Result<User, Error> {
        if self.username_is_censored(username) > Probability::new(0.8) {
            return Err(Error::InvalidUsername)
        }

        // ...
    }
}

#[cgp_impl(new GetUserWithPostgres)]
impl UserGetter {
    fn get_user(&self, #[implicit] database: &PostgresDb, user_id: &UserId) -> Result<User, Error> {
        // ...
    }
}
```

Instead of having a monolithic `PostgresUserManager` provider, we now have fine grained providers like `CreateUserWithPostgres` and `GetUserWithPostgres` that implement each fine grained trait separately. We can also see that the dependency to `CanCensorUsername` is only present in the implementation of `CreateUserWithPostgres`, while other providers like `GetUserWithPostgres` can work fine without requiring that trait to be implemented by the context.

### Higher-order providers

Another key advantage of using fine grained traits is that we can now easily define *higher-order providers* that wrap around other provider implementations. For example, we can extra the logic of banning censored username into a separate provider like follows:

```rust
#[cgp_impl(new FilterCensoredUsername<InnerCreator>)]
#[uses(CanCensorUsername)]
#[use_provider(InnerCreator: UserCreator)]
impl<InnerCreator> UserCreator {
    fn create_user(&self, username: &str, email: &Email) -> Result<User, Error> {
        if self.username_is_censored(username) > Probability::new(0.8) {
            return Err(Error::InvalidUsername);
        }

        InnerCreator::create_user(self, username, email)
    }
}

#[cgp_impl(new CreateUserWithPostgres)]
impl UserCreator {
    fn create_user(
        &self,
        #[implicit] database: &PostgresDb,
        username: &str,
        email: &Email,
    ) -> Result<User, Error> {
        // ...
    }
}
```

In the example above, we introduce a higher-order provider called `FilterCensoredUsername`, which can wrap around an inner provider for `UserCreator`. It would reject a call to `create_user` based on the result from `CanCensorUsername`. Otherwise, it forwards the call to the inner provider.

With this separation of concern, we can now remove the dependency on `CanCensorUsername` from `CreateUserWithPostgres`, which can now focus purely on constructing the SQL insert query. Instead of always filtering the username, the logic becomes composable, allowing the concrete context to choose either just `CreateUserWithPostgres` or the combined `FilterCensoredUsername<CreateUserWithPostgres>` provider to handle user creation.

This separation of concern also allows logic like `FilterCensoredUsername` to be reused with other inner providers. For example, suppose that we also have a separate `CreateUserWithSqlite` provider that can be used by a local-first application. We can now enable the filtering of user creation using `FilterCensoredUsername<CreateUserWithSqlite>`.

### Too much wiring with fine grained traits

As we can see, the use of fine grained traits and higher order providers allows us to nicely decompose and decouple the dependencies that each trait needs. However, the main issue with this approach is that the boilerplate for wiring the components become significantly more verbose. For instance, the wiring for `ProductionApp` would become:

```rust
delegate_components! {
    ProductionApp {
        UserCreatorComponent:
            FilterCensoredUsername<CreateUserWithPostgres>,
        UserGetterComponent:
            GetUserWithPostgres,
        UserUpdaterComponent:
            UpdateUserWithPostgres,
        PostCreatorComponent:
            FilterSpamMessage<CreatePostWithPostgres>,
        PostGetterComponent:
            GetPostWithPostgres,
        PostUpdaterComponent:
            UpdatePostWithPostgres,
        PostDeleterComponent:
            DeletePostWithPostgres,
        UsernameCensorComponent:
            AiUserCensor,
        SpamMessageDetectorComponent:
            AiSpamMessageDetector,
    }
}
```

Compared to before, there are now 9 component entries in `ProductionApp`, as compared to the list of 4 components earlier. And given that this example only include minimal features, it is not uncommon for real world applications to have dozens if not hundreds of component wirings if fine grained traits are used.

This presents a significant challenge to spread the adoption of CGP. To the eyes of an untrained developers, the hundreds of lines of component wirings are noise that brings confusion on what `ProductionApp` really implements.

If we consider the principles of good programming practices, the real problem with the code above is that too much information are presented at once. What we need is to group the component wirings back into smaller sub-units, so that they can be read and understood piece by piece.

For example, we could group the user-related traits together as follows:

```rust
delegate_components! {
    new PostgresUserComponents {
        UserCreatorComponent:
            FilterCensoredUsername<CreateUserWithPostgres>,
        UserGetterComponent:
            GetUserWithPostgres,
        UserUpdaterComponent:
            UpdateUserWithPostgres,
    }
}
```

With the code above, we define an *aggregated provider* called `PostgresUserComponents` which encapsulates all user-related CGP traits. Since this standalone definition only contains 3 entries, it is much more manageable to understand what this aggregated provider implements.

Similarly, we can define a `PostgresPostComponents` to group all post-related CGP traits, and a `ContentFilterComponents` to group the username and spam message filters.

### The challenges of grouping delegate component keys

However, before the current v0.7.1 release, even though we have ways to group CGP component wirings, there lacked good developer experience for using these aggregated providers at the top-level component wiring. For example, the component wiring for `ProductionApp` can at best be simplified into:

```rust
delegate_components! {
    ProductionApp {
        [
            UserCreatorComponent,
            UserGetterComponent,
            UserUpdaterComponent,
        ]:
            PostgresUserComponents,
        [
            PostCreatorComponent,
            PostGetterComponent,
            PostUpdaterComponent,
            PostDeleterComponent,
        ]:
            PostgresPostComponents,
        [
            UsernameCensorComponent,
            SpamMessageDetectorComponent,
        ]:
            ContentFilterComponents,
    }
}
```

In the code above, we make use of the array notation to forward a group of keys, such as `UserCreatorComponent`, `UserGetterComponent`, and `UserUpdaterComponent`, all to the same aggregated provider, i.e. `PostgresUserComponents`.

The problem we have here is that CGP had no way encapsulate the group of component keys used in the wiring. What we really wanted is to express something like follows:

```rust
delegate_components! {
    ProductionApp {
        ???: // all user components
            PostgresUserComponents,
        ???: // all post components
            PostgresPostComponents,
        ???: // all content filter components
            ContentFilterComponents,
    }
}
```

However, due to how CGP internally makes use of the trait system, it is not possible to directly express something like *"implement `DelegateComponent` for these list of types"* with Rust's existing trait system.

The closest technique that CGP could use is to use macros to expand the identifier, such as:

```rust
delegate_components! {
    ProductionApp {
        all_user_components!():
            PostgresUserComponents,
        all_post_components!():
            PostgresPostComponents,
        all_content_filter_components!():
            ContentFilterComponents,
    }
}
```

where the macros like `all_user_components!()` expand into `[UserCreatorComponent, UserGetterComponent, UserUpdaterComponent]`. But even this wouldn't work, because Rust macros are expanded lazily, meaning that `delegate_components!` could only see the unexpanded literal `all_user_components!()`, and thus cannot properly desugar the entries.

Furthermore, there is no easy way for CGP to generate macros like `all_user_components!()` for the user. That is, there are limited support in Rust's macro system to allow macros to generate and export new macros.

### The problems with CGP presets

Since the early days of the project, we have experimented with various ways to work around the limitations of Rust macros, and implemented a [**preset system**](/blog/hypershell-release#cgp-presets) system to group a collection of component wirings together to form a preset. However, there are many issues with providing a good developer experience through CGP presets.

With CGP presets, we could define a `PostgresUserComponents` preset like follows:

```rust
cgp_preset! {
    PostgresUserComponents {
        UserCreatorComponent:
            FilterCensoredUsername<CreateUserWithPostgres>,
        UserGetterComponent:
            GetUserWithPostgres,
        UserUpdaterComponent:
            UpdateUserWithPostgres,
    }
}
```

and then use the components by inheriting it in `ProductionApp`:

```rust
#[cgp_inherit(PostgresUserComponents)]
pub struct ProductionApp { /* ... */ }

delegate_components! {
    ProductionApp {
        // No need to delegate entries in PostgresUserComponents
        // ...
    }
}
```

However, the biggest limitation of CGP presets is that it supports only a single-inheritance-like hierarchy of components. This means that since `ProductionApp` has "inherited" `PostgresUserComponents`, it cannot also inherit another preset like `PostgresPostComponents` due to the coherence restrictions in Rust.

We have also experimented on a multiple-inheritance-like feature with CGP presets using macros. However, the lack of eager macro evaluation and hygenic bindings of imports make it tedious to use the feature.

## Introducing CGP namespaces and paths

Fortunately, with CGP v0.7.1, we have managed to solve the long-standing problem and devise a way to group component keys through a new feature called **namespaces**.

The way CGP namespaces work is as follows. For each CGP component definition, we can define a namespace prefix like follows:

```rust
#[cgp_component(UserCreator)]
#[namespace(@app.core.user)]
pub trait CanCreateUser {
    fn create_user(&self, username: &str, email: &Email) -> Result<User, Error>;
}
```

In the code above, we add a new `#[namespace]` attribute to the `UserCreator` component, with a prefix `@app.core.user`. This prefix acts as the new group "key" that we will use later in `delegate_components!`.

CGP allows the same namespace prefix to be used by multiple traits. For example, we can also apply the `@app.core.user` prefix to `UserGetter`, and similarly to `UserUpdater`:

```rust
#[cgp_component(UserGetter)]
#[namespace(@app.core.user)]
pub trait CanGetUser {
    fn get_user(&self, user_id: &UserId) -> Result<User, Error>;
}
```

Similarly, we can assign the prefix `@app.core.post` to `PostCreator`, and other post-related traits:

```rust
#[cgp_component(PostCreator)]
#[namespace(@app.core.post)]
pub trait CanCreatePost {
    fn create_post(&self, title: &str, content: &str) -> Result<Post, Error>;
}
```

We would also assign the prefix `@app.core.content_filter` to `UsernameCensor` and `SpamMessageDetector`.

After assigning the namespace prefixes, we can now use them to bulk delegate the CGP components in the top-level wiring for `ProductionApp`:

```rust
delegate_components! {
    ProductionApp {
        namespace default;

        @app.core.user: PostgresUserComponents,
        @app.core.post: PostgresPostComponents,
        @app.extra.content_filter: ContentFilterComponents,
    }
}
```

Compared to before, our new definition for `ProductionApp` becomes significantly shorter and concise. Since namespace is an opt-in feature, we explicitly enable it using the `namespace` keyword inside the `delegate_components!` block. The `default` namespace is used here, but as we will see in later sections, it is also possible to define custom namespaces and assign different prefixes to CGP components.

Following that, a delegate key like `@app.core.user` implicitly forwards all implementation of the user-related CGP traits to the aggregated provider `PostgresUserComponents`. Similarly, the next two entries delegate the corresponding CGP components to the respective aggregated providers.

CGP namespaces allows us to group CGP component keys into a hierarchy of prefixes. This in turns allows us to cleanly encapsulate group of CGP components, and break down the wiring configuration into smaller parts.
