# CGP v0.8.0 - cargo-cgp, new documentation, and namespaces

**CGP v0.8.0 has been released with improvements to debugging, documentation, and component wiring.** Alongside the release, cargo-cgp helps explain wiring failures. The website now provides reference material, conceptual explanations, and project walkthroughs, while namespaces let growing applications group related wiring and make configuration differences easier to see.

Context-Generic Programming (CGP) is a language extension for Rust, with pluggable trait implementations at compile-time. It is an ordinary library on stable Rust: applications select providers through wiring that resolves to static calls. You can adopt it one component at a time. ## Diagnosing wiring with cargo-cgp

Verbose and confusing compiler errors have been one of the largest obstacles to adopting CGP since the project began. Even a simple mistake, such as forgetting a field or a component binding, can produce a diagnostic naming generated traits and type-level encodings of fields or paths. CGP uses that machinery to support interchangeable implementations, but the compiler reports errors in terms of the Rust it receives after macro expansion.

Diagnosing a small mistake can require newcomers to understand advanced Rust traits and generics, together with the internal details of CGP. A developer can understand what their code is supposed to do and still struggle to work out why it does not compile. Better syntax alone does not address that barrier.

[cargo-cgp v0.1.0](/docs/cargo-cgp) helps developers find missing dependencies without reconstructing the generated code first. I am introducing this separate tool for checking CGP code and inspecting macro expansions alongside CGP v0.8.0. `cargo cgp check` leads with the root cause for the classes it recognizes, and the tool does not yet reshape every class.

### Find a missing field

A missing `height` field demonstrates how cargo-cgp explains a wiring failure. In this example from the [area-calculation tutorial](/docs/tutorials/area-calculation/static-dispatch), the context is `Rectangle` itself, the value being operated on. Its area provider needs both `width` and `height`, but the struct supplies only `width`.

Save this library example as `src/lib.rs` in a Cargo package using `cgp = "0.8.0"`:

```rust
use cgp::prelude::*;

#[cgp_component(AreaCalculator)]
pub trait CanCalculateArea {
    fn area(&self) -> f64;
}

#[cgp_impl(new RectangleArea)]
impl AreaCalculator {
    fn area(&self, #[implicit] width: f64, #[implicit] height: f64) -> f64 {
        width * height
    }
}

#[derive(HasField)]
pub struct Rectangle {
    pub width: f64,
    // missing `height` field
}

delegate_and_check_components! {
    Rectangle {
        AreaCalculatorComponent: RectangleArea,
    }
}
```

The wiring check fails because `RectangleArea` requires a field that `Rectangle` lacks. `RectangleArea` reads its implicit arguments from the context's fields, and the wiring selects it for `AreaCalculatorComponent`. `delegate_and_check_components!` checks that the provider's dependencies are satisfied. Running `cargo cgp check` identifies the missing field:

```text

  --> src/lib.rs:23:9
   |
23 |         AreaCalculatorComponent: RectangleArea,
   |         ^^^^^^^^^^^^^^^^^^^^^^^
   |
   = note: root cause: [CGP-E110] missing field `height` on `Rectangle`
           this is required through the dependency chain:
             [CGP-E101] consumer trait impl `CanCalculateArea` for context `Rectangle`
             └─ [CGP-E102] provider trait impl `AreaCalculator` with context `Rectangle` for provider `RectangleArea`
               └─ [CGP-E110] missing field `height` on `Rectangle`
   = help: add the field `height: f64` to `Rectangle`
```

The rewritten diagnostic names the missing field and the change needed to supply it. Its dependency tree explains why the field is required. Plain `cargo check` reports the same mistake through generated traits and a nested `Symbol` type:

Add the field to repair the program:

```rust
#[derive(HasField)]

    pub width: f64,
    pub height: f64,
}
```

Adding `height` makes the wiring check pass. The provider can then read both fields and calculate the area.

cargo-cgp extracts the root cause through the Rust compiler's API. It wraps a nightly compiler, uses that API to inspect the failed dependencies, and formats their chain. This gives it access to information that would otherwise be difficult to recover from the printed diagnostic alone.

### Try the checker

Install cargo-cgp with cargo and rustup, then run it inside your CGP project. The installation commands build the front-end and provision its compiler-linked driver:

```sh
cargo install cargo-cgp
cargo cgp setup
# Run this from your CGP project's directory:
cargo cgp check
```

cargo-cgp's nightly is separate from your application's normal toolchain. `cargo cgp setup` installs the tool's pinned nightly and builds the matching driver for its checks. Your application keeps its normal toolchain for ordinary cargo builds, and CGP itself still compiles on stable Rust. cargo-cgp is optional.

The tool is tested on Linux. macOS and Windows are untested.

Use plain cargo to build, run, and test applications. cargo-cgp supplies `check` for diagnostics and [`expand`](/docs/cargo-cgp/expand) for reading the Rust generated by macros, with CGP's type-level constructs restored to readable notation. The [installation guide](/docs/cargo-cgp/installation) covers setup, updates, and the Nix alternative.

## Grouping component wiring with namespaces

Flat wiring tables can make growing CGP applications difficult to understand. Splitting an application into reusable providers makes dependencies easier to isolate, but each component also needs a routing entry in a flat `delegate_components!` table. As the component count grows, that list can obscure which choices matter and make the application look more complicated than the behavior it implements.

Provider bundles did not remove repeated component lists from top-level wiring. CGP could already bundle implementations, but applications still had to enumerate the corresponding component keys. The preset system was an earlier attempt to reduce that repetition, with limitations explained below.

Namespaces let an application select related implementations as a group. In the example below, production and test configurations share a PostgreSQL-backed core and differ in their content filters. A table that lists every component becomes a table selecting those groups, making the difference between configurations visible in one entry.

You can skip the motivation if you already know why flat wiring tables become difficult to maintain. Jump to [the namespace syntax](#introducing-cgp-namespaces-and-paths), or to [the migration guide](#breaking-changes-and-migration) if you are upgrading an existing application. The walkthrough below builds up the wiring problem before introducing the solution.

### Start with a manager per domain {#an-example-social-media-web-app}

The running example uses an application context to select the operations of a social-media service. It holds a database handle and chooses the implementations for managing users and posts. Here the context represents the service, while the earlier `Rectangle` context was the data being operated on.

The snippets illustrate wiring rather than a complete web service. They assume `use cgp::prelude::*;` and omit domain type declarations and database query bodies. The [web-app walkthrough](/docs/projects/cgp-examples/web-app) follows the same example, and its [compiling source](https://github.com/contextgeneric/cgp-examples/tree/v0.8.0/web-app) uses placeholder database operations.

Each stage replaces the preceding definitions or wiring. Treat a revised provider or table as a replacement, rather than adding a second implementation beside the previous one.

The initial design groups user and post operations into a manager trait per domain:

```rust
#[cgp_component(UserManager)]
pub trait CanManageUser {
    fn create_user(&self, username: &str, email: &Email) -> Result<User, Error>;

    fn get_user(&self, user_id: &UserId) -> Result<User, Error>;

    fn update_user_data(&self, user_id: &UserId, user_data: &UserData) -> Result<(), Error>;
}

#[cgp_component(PostManager)]
pub trait CanManagePost {
    fn create_post(&self, title: &str, content: &str) -> Result<Post, Error>;

    fn get_post(&self, post_id: &PostId) -> Result<Post, Error>;

    fn update_post(&self, post_id: &PostId, content: &str) -> Result<(), Error>;

    fn delete_post(&self, post_id: &PostId) -> Result<(), Error>;
}
```

`#[cgp_component]` separates each trait's calling interface from its provider implementations. It turns the ordinary trait into a CGP component, generating a provider trait such as `UserManager` and a wiring key such as `UserManagerComponent`. A provider implements the operations independently of a concrete application, and the application's wiring chooses which provider to use.

Grouping items in a component makes one provider choice decide their implementations together. Component traits can contain multiple methods, associated types, and constants, so grouping the manager methods is a design choice.

The database providers can remain independent of any concrete application context:

```rust
#[cgp_impl(new PostgresUserManager)]
impl UserManager {
    fn create_user(
        &self,
        #[implicit] database: &PostgresDb,
        username: &str,
        email: &Email,
    ) -> Result<User, Error> {
        // ...
    }

    fn get_user(
        &self,
        #[implicit] database: &PostgresDb,
        user_id: &UserId,
    ) -> Result<User, Error> {
        // ...
    }

    fn update_user_data(
        &self,
        #[implicit] database: &PostgresDb,
        user_id: &UserId,
        user_data: &UserData,
    ) -> Result<(), Error> {
        // ...
    }
}

#[cgp_impl(new PostgresPostManager)]
impl PostManager {
    fn create_post(
        &self,
        #[implicit] database: &PostgresDb,
        title: &str,
        content: &str,
    ) -> Result<Post, Error> {
        // ...
    }

    fn get_post(
        &self,
        #[implicit] database: &PostgresDb,
        post_id: &PostId,
    ) -> Result<Post, Error> {
        // ...
    }

    fn update_post(
        &self,
        #[implicit] database: &PostgresDb,
        post_id: &PostId,
        content: &str,
    ) -> Result<(), Error> {
        // ...
    }

    fn delete_post(
        &self,
        #[implicit] database: &PostgresDb,
        post_id: &PostId,
    ) -> Result<(), Error> {
        // ...
    }
}
```

Both providers read a PostgreSQL `database` field through their implicit arguments. Any context supplying that dependency can reuse the implementations. We could also define `SqliteUserManager` and `SqlitePostManager` providers for a SQLite-backed application, without changing the manager interfaces.

The initial production configuration needs only two entries:

```rust
#[derive(HasField)]
pub struct ProductionApp {
    pub database: PostgresDb,
}

delegate_and_check_components! {
    ProductionApp {
        UserManagerComponent: PostgresUserManager,
        PostManagerComponent: PostgresPostManager,
    }
}
```

`ProductionApp` selects both managers without coupling their implementations to that context. At this stage, the database field is their only dependency.

### Add dependencies as the service grows

Content filtering adds dependencies to the database-backed managers. As the service grows, user creation needs username filtering and post creation needs spam detection, so the managers acquire dependencies on two more components:

```rust
#[cgp_component(UsernameCensor)]
pub trait CanCensorUsername {
    fn username_is_censored(&self, username: &str) -> Probability;
}

#[cgp_component(SpamMessageDetector)]
pub trait CanDetectSpamMessage {
    fn message_is_spam(&self, message: &str) -> Probability;
}

#[cgp_impl(new PostgresUserManager)]
#[uses(CanCensorUsername)]
impl UserManager {
    fn create_user(
        &self,
        #[implicit] database: &PostgresDb,
        username: &str,
        email: &Email,
    ) -> Result<User, Error> {
        if self.username_is_censored(username) > Probability::new(0.8) {
            return Err(Error::InvalidUsername);
        }

        // ...
    }

    // ...
}

#[cgp_impl(new PostgresPostManager)]
#[uses(CanDetectSpamMessage)]
impl PostManager {
    fn create_post(
        &self,
        #[implicit] database: &PostgresDb,
        title: &str,
        content: &str,
    ) -> Result<Post, Error> {
        if self.message_is_spam(content) > Probability::new(0.8) {
            return Err(Error::InvalidMessage);
        }

        // ...
    }

    // ...
}
```

The managers use the filter scores to decide whether to reject a user or post. `CanCensorUsername` and `CanDetectSpamMessage` return the scores compared with the threshold. `#[uses]` declares each trait dependency on the context, while `#[implicit] database` reads its database field. The remaining manager methods are omitted here.

Production and tests can share the database providers while choosing different filters. Production filtering may involve an AI model or a cloud service, while tests can use deterministic string matching to exercise the rest of the application more quickly:

```rust
#[derive(HasField)]
pub struct ProductionApp {
    pub database: PostgresDb,
}

delegate_components! {
    ProductionApp {
        UserManagerComponent: PostgresUserManager,
        PostManagerComponent: PostgresPostManager,
        UsernameCensorComponent: AiUserCensor,
        SpamMessageDetectorComponent: AiSpamMessageDetector,
    }
}

#[derive(HasField)]
pub struct TestApp {
    pub database: PostgresDb,
}

delegate_components! {
    TestApp {
        UserManagerComponent: PostgresUserManager,
        PostManagerComponent: PostgresPostManager,
        UsernameCensorComponent: DummyUserCensor,
        SpamMessageDetectorComponent: DummySpamMessageDetector,
    }
}
```

Both contexts reuse the PostgreSQL managers and supply the fields those managers require. Their different filter choices distinguish production from testing. `#[derive(HasField)]` makes each context's `database` field available to the providers' implicit arguments.

These tables record choices without checking all their dependencies. Explicit component checks, shown below, verify that the selected providers can be used.

Adding dependencies also increases the wiring repeated across contexts. CGP lets the application's dependency tree grow as requirements are added, but four component entries on each of two contexts already means eight wiring entries.

### Split independently reusable operations {#fine-grained-traits}

A manager provider makes every operation require all of that provider's dependencies. `get_user` needs the database, but it also requires a context implementing `CanCensorUsername` because that bound belongs to `PostgresUserManager`. The post manager has the same problem with spam detection. As more methods acquire unrelated dependencies, the manager becomes harder to maintain and test.

Domain names also leave questions about which operations belong together. Should `get_user_profile_picture` be part of the user manager, and should `get_user_posts` belong to the user or post manager? A single domain name does not always identify the right group of operations.

Narrower trait bounds let generic code request fewer operations. If a user manager gains a destructive `delete_user` operation, code that only retrieves users should not have to depend on the whole manager interface. Separate bounds let that code require only the operations it needs.

Fine-grained components, each containing one or a handful of related items, let each provider require only what it uses:

```rust
#[cgp_component(UserCreator)]
pub trait CanCreateUser {
    fn create_user(&self, username: &str, email: &Email) -> Result<User, Error>;
}

#[cgp_component(UserGetter)]
pub trait CanGetUser {
    fn get_user(&self, user_id: &UserId) -> Result<User, Error>;
}

#[cgp_component(UserUpdater)]
pub trait CanUpdateUser {
    fn update_user_data(&self, user_id: &UserId, user_data: &UserData) -> Result<(), Error>;
}
```

The user-creation provider needs the censor, while the getter needs only the database:

```rust
#[cgp_impl(new CreateUserWithPostgres)]
#[uses(CanCensorUsername)]
impl UserCreator {
    fn create_user(
        &self,
        #[implicit] database: &PostgresDb,
        username: &str,
        email: &Email,
    ) -> Result<User, Error> {
        if self.username_is_censored(username) > Probability::new(0.8) {
            return Err(Error::InvalidUsername);
        }

        // ...
    }
}

#[cgp_impl(new GetUserWithPostgres)]
impl UserGetter {
    fn get_user(&self, #[implicit] database: &PostgresDb, user_id: &UserId) -> Result<User, Error> {
        // ...
    }
}
```

The dependencies now follow the individual operations. `CreateUserWithPostgres` imports `CanCensorUsername`, while `GetUserWithPostgres` does not. The post manager can be split in the same way into creation, retrieval, update, and deletion components. Generic code bounded by `CanGetUser` can retrieve users without requiring user creation or deletion.

### Separate filtering from database access

A filtering wrapper can now add the username check to any user-creation provider:

```rust
#[cgp_impl(new FilterCensoredUsername<InnerCreator>)]
#[uses(CanCensorUsername)]
#[use_provider(InnerCreator: UserCreator)]
impl<InnerCreator> UserCreator {
    fn create_user(&self, username: &str, email: &Email) -> Result<User, Error> {
        if self.username_is_censored(username) > Probability::new(0.8) {
            return Err(Error::InvalidUsername);
        }

        InnerCreator::create_user(self, username, email)
    }
}

#[cgp_impl(new CreateUserWithPostgres)]
impl UserCreator {
    fn create_user(
        &self,
        #[implicit] database: &PostgresDb,
        username: &str,
        email: &Email,
    ) -> Result<User, Error> {
        // ...
    }
}
```

`FilterCensoredUsername` is a **higher-order provider**: it takes another provider as a parameter. `#[use_provider]` requires that inner provider to implement user creation for the same context. The wrapper rejects censored names and otherwise calls the inner provider.

Filtering is now a wiring choice separate from database access. `CreateUserWithPostgres` can focus on constructing the SQL insert query, while the context chooses either that provider directly or `FilterCensoredUsername<CreateUserWithPostgres>`. A local-first application could reuse the wrapper as `FilterCensoredUsername<CreateUserWithSqlite>`, without changing the filtering implementation.

`FilterSpamMessage<InnerCreator>` applies the same separation to post creation. It uses `CanDetectSpamMessage` to reject spam, then forwards an allowed post to its inner `PostCreator`. The wiring can therefore choose `FilterSpamMessage<CreatePostWithPostgres>` independently of the database provider's implementation.

### Count the cost of the separation

The smaller components isolate dependencies and make the filtering reusable, but they add wiring. With seven CRUD operations and two filters, the production table becomes:

```rust
delegate_components! {
    ProductionApp {
        UserCreatorComponent:
            FilterCensoredUsername<CreateUserWithPostgres>,
        UserGetterComponent:
            GetUserWithPostgres,
        UserUpdaterComponent:
            UpdateUserWithPostgres,
        PostCreatorComponent:
            FilterSpamMessage<CreatePostWithPostgres>,
        PostGetterComponent:
            GetPostWithPostgres,
        PostUpdaterComponent:
            UpdatePostWithPostgres,
        PostDeleterComponent:
            DeletePostWithPostgres,
        UsernameCensorComponent:
            AiUserCensor,
        SpamMessageDetectorComponent:
            AiSpamMessageDetector,
    }
}
```

The small example now needs nine component entries instead of four. An application with more features can grow to dozens or hundreds of wiring entries. To someone unfamiliar with the code, that list can obscure what `ProductionApp` implements and make adopting CGP look harder than it needs to be.

Grouping the bindings would let a reader understand one part of the application at a time. The flat table presents too much information at once, so it needs smaller units.

A provider bundle can collect related bindings into a smaller table:

```rust
delegate_components! {
    new PostgresUserComponents {
        UserCreatorComponent:
            FilterCensoredUsername<CreateUserWithPostgres>,
        UserGetterComponent:
            GetUserWithPostgres,
        UserUpdaterComponent:
            UpdateUserWithPostgres,
    }
}
```

`new PostgresUserComponents` declares an **aggregate provider**, a provider whose table delegates each operation to another provider. Its three entries can be read independently of the rest of the application. `PostgresPostComponents` can collect the post operations, and `AiContentFilterComponents` can collect the AI-backed filtering providers.

Bundles organize the implementations, but without namespaces the application must still enumerate every key when forwarding to them:

```rust
delegate_components! {
    ProductionApp {
        [
            UserCreatorComponent,
            UserGetterComponent,
            UserUpdaterComponent,
        ]:
            PostgresUserComponents,
        [
            PostCreatorComponent,
            PostGetterComponent,
            PostUpdaterComponent,
            PostDeleterComponent,
        ]:
            PostgresPostComponents,
        [
            UsernameCensorComponent,
            SpamMessageDetectorComponent,
        ]:
            AiContentFilterComponents,
    }
}
```

Array keys still leave each component group unnamed. They send several components to the same bundle, but the application cannot refer to “all user components” or “all content filters” as a group. Adding a user operation therefore means updating both the bundle and the component list on each application that forwards to it.

### Why the earlier grouping approaches were insufficient

The desired configuration would let us name each group once. In pseudocode, it would look like this:

```text
delegate_components! {
    ProductionApp {
        ???: // all user components
            PostgresUserComponents,
        ???: // all post components
            PostgresPostComponents,
        ???: // all content filter components
            AiContentFilterComponents,
    }
}
```

Rust's trait system does not provide an operation that expands a type-level list into a separate implementation for every listed key. CGP therefore needs a way to express the grouping through its own lookup rules or macro expansion.

A macro that expands to a list of component keys might appear to solve the repetition. Another hypothetical form is:

```text
delegate_components! {
    ProductionApp {
        all_user_components!():
            PostgresUserComponents,
        all_post_components!():
            PostgresPostComponents,
        all_content_filter_components!():
            AiContentFilterComponents,
    }
}
```

The proposed helpers would supply a component list for each group. For example, `all_user_components!()` would expand to `[UserCreatorComponent, UserGetterComponent, UserUpdaterComponent]`, with corresponding lists for posts and filters. These are hypothetical forms, not supported syntax.

The outer macro cannot inspect a helper's output when it parses the invocation. `delegate_components!` receives `all_user_components!()` before the helper expands, so the component list is unavailable to its parser. Supporting this arrangement would require a different macro-composition mechanism, together with machinery for generating and exporting helpers whose names and imports remain usable across crate boundaries.

My earlier [preset system](/blog/hypershell-release#cgp-presets) shared wiring but made independent groups difficult to combine. Its inheritance mechanism could supply one preset to a context, while Rust's coherence restrictions prevented a context from inheriting independent user and post presets that way. I also experimented with macro-based composition of multiple presets, but expansion order and the handling of imports and aliases made that approach tedious to use.

Namespaces let an application name a component group and select its implementation bundle without enumerating every key. That is the goal the earlier approaches were trying to meet. Namespaces express it through trait resolution and paths. The [migration section](#replace-presets-with-namespace-configuration) shows how existing preset users can move to them.

### Give component groups a path {#introducing-cgp-namespaces-and-paths}

A component can register a path prefix in a namespace. Here, `CanCreateUser` registers its component under `@app.core.user` in the built-in `DefaultNamespace`:

```rust
#[cgp_component(UserCreator)]
#[prefix(@app.core.user in DefaultNamespace)]
pub trait CanCreateUser {
    fn create_user(&self, username: &str, email: &Email) -> Result<User, Error>;
}
```

`#[prefix]` records the route, and CGP appends the component marker to it. A lookup for `UserCreatorComponent` therefore uses the address `@app.core.user.UserCreatorComponent` once a context joins the namespace.

Several components can share one prefix. The getter below and the updater register under the same user prefix:

```rust
#[cgp_component(UserGetter)]
#[prefix(@app.core.user in DefaultNamespace)]
pub trait CanGetUser {
    fn get_user(&self, user_id: &UserId) -> Result<User, Error>;
}
```

The post components register under `@app.core.post`:

```rust
#[cgp_component(PostCreator)]
#[prefix(@app.core.post in DefaultNamespace)]
pub trait CanCreatePost {
    fn create_post(&self, title: &str, content: &str) -> Result<Post, Error>;
}
```

The filter components register under `@app.extra.content_filter`, also in `DefaultNamespace`. These paths describe the groups independently of which providers an application chooses.

The application joins the namespace and forwards each group to its bundle:

```rust
delegate_components! {
    ProductionApp {
        namespace DefaultNamespace;

        @app.core.user: PostgresUserComponents,
        @app.core.post: PostgresPostComponents,
        @app.extra.content_filter: AiContentFilterComponents,
    }
}
```

Namespace routing connects each component lookup to the application's selected provider bundle. The namespace supplies routes, prefixes identify groups, and aggregate providers supply implementations. For example, `create_user` asks for `UserCreatorComponent`, which the namespace redirects to `@app.core.user.UserCreatorComponent`. The `@app.core.user` entry selects `PostgresUserComponents`, and that bundle selects `FilterCensoredUsername<CreateUserWithPostgres>` for the component. Rust resolves these steps at compile time, without a runtime lookup table.

Namespaces are opt-in: `namespace DefaultNamespace;` enables the registered routes for this table. A custom namespace can register components under different prefixes and be selected in the same way.

The top-level table now has three entries. The individual bindings still live in the bundles, but the application no longer repeats their component names merely to select a group.

### Group paths hierarchically

Parent prefixes can group several domains. The path `@app.core.user` has the parent `@app.core`, which itself sits under `@app`. Both user and post components share `@app.core`, so an intermediate bundle can collect them, with another bundle collecting the extras:

```rust
delegate_components! {
    new PostgresCoreComponents {
        namespace DefaultNamespace;

        @app.core.user: PostgresUserComponents,
        @app.core.post: PostgresPostComponents,
        // other core components
    }
}

delegate_components! {
    new ProductionExtraComponents {
        namespace DefaultNamespace;

        @app.extra.content_filter: AiContentFilterComponents,
        // other extra components
    }
}
```

Path-keyed bundles must also join `DefaultNamespace` to resolve the component keys they receive. A bundle receives the bare component key, and its namespace statement redirects that key to the paths inside its own table. Leaf bundles keyed by bare component names do not need a namespace statement.

The production configuration now selects two groups:

```rust
delegate_components! {
    ProductionApp {
        namespace DefaultNamespace;

        @app.core: PostgresCoreComponents,
        @app.extra: ProductionExtraComponents,
    }
}
```

A test configuration can share the whole PostgreSQL-backed core and change just the extras. Its `DummyExtraComponents` bundle supplies the deterministic filters:

```rust {6}
delegate_components! {
    TestApp {
        namespace DefaultNamespace;

        @app.core: PostgresCoreComponents,
        @app.extra: DummyExtraComponents,
    }
}
```

A local configuration can instead change the database-backed core while retaining the production filters:

```rust {5}
delegate_components! {
    LocalApp {
        namespace DefaultNamespace;

        @app.core: SqliteCoreComponents,
        @app.extra: ProductionExtraComponents,
    }
}
```

The two variants differ from production in one entry each: `TestApp` changes `@app.extra`, while `LocalApp` changes `@app.core`.

Each context must still supply the fields and other dependencies its selected providers require. A SQLite core would need its corresponding database handle.

Named groups make the configuration differences easier to compare. Without namespace grouping, a reader would have to compare the individual component entries across all three contexts. Those entries might appear in different orders, making the differences harder to spot. Grouping shows the shared parts and the parts that change directly.

### Check the completed configuration

Check each concrete context explicitly to verify its provider dependencies. Wiring records provider choices lazily, so a `delegate_components!` block can compile before any operation forces those dependencies to be checked:

```rust
check_components! {
    ProductionApp {
        UserCreatorComponent,
        UserGetterComponent,
        UserUpdaterComponent,
        PostCreatorComponent,
        PostGetterComponent,
        PostUpdaterComponent,
        PostDeleterComponent,
        UsernameCensorComponent,
        SpamMessageDetectorComponent,
    }
}
```

`ProductionApp`, `TestApp`, and local variants can use the same nine-component check. Apply the check above to `TestApp` and any local variant as well. For an earlier stage of the walkthrough, check the components used in that stage, such as `UserManagerComponent` and `PostManagerComponent` before the managers are split.

Component checks must still name the operations that need to work. Namespaces remove repeated routing entries, but the dependencies of those operations still need verification. Check aggregate providers through the real contexts that use them, rather than treating a bundle as its own application context.

The [namespace documentation](/docs/concepts/namespaces) explains the lookup model, and the [`delegate_components!` reference](/docs/reference/macros/delegate_components) covers the path syntax.

## Sharing default implementations {#default-implementations}

A namespace can also bind provider choices shared by all its contexts. The bundles above suit configurations that swap whole implementation groups, such as `SqliteCoreComponents`, `PostgresCoreComponents`, or a `PostgresWithLoggingCoreComponents` variant that adds logging.

An early application may not need interchangeable provider bundles. If it only uses PostgreSQL, defining a `PostgresUserComponents` bundle may be more organization than it needs yet. A single chosen implementation, intentionally coupled to its interface within a configuration, can be easier to reason about.

Default implementations record fixed provider choices within a namespace. If several contexts should always use the same user and post providers, a custom namespace can record those choices once, leaving explicit wiring for the choices that vary.

Define a namespace inheriting the component routes from `DefaultNamespace`:

```rust
cgp_namespace! {
    new DefaultAppComponents: DefaultNamespace
}
```

`DefaultAppComponents` inherits the prefixes and any default bindings supplied by `DefaultNamespace`. Its own bindings apply to contexts that select this configuration namespace, without changing what other namespaces select.

Add `#[default_impl]` to the earlier `GetUserWithPostgres` implementation to bind it at the component's full path:

```rust
#[cgp_impl(new GetUserWithPostgres)]
#[default_impl(@app.core.user.UserGetterComponent in DefaultAppComponents)]
impl UserGetter {
    fn get_user(&self, #[implicit] database: &PostgresDb, user_id: &UserId) -> Result<User, Error> {
        // ... query the database
    }
}
```

The attribute registers `GetUserWithPostgres` at that path in `DefaultAppComponents`. It is equivalent to writing the binding separately in a namespace body:

```rust
cgp_namespace! {
    DefaultAppComponents {
        @app.core.user.UserGetterComponent: GetUserWithPostgres,
    }
}
```

Namespace-body entries bind providers for every context that selects the namespace. The body resembles a `delegate_components!` table, but its entries belong to the namespace instead of one context or aggregate provider. The full `@app.core.user.UserGetterComponent` path is required here because the inherited route already maps the bare component marker to that address.

Use either the attribute or the namespace-body entry for this binding, rather than writing both.

A prefixed default registration must live in the crate that owns its namespace, here `DefaultAppComponents`. The key expands to CGP's `PathCons` type, so owning a component marker nested inside it does not satisfy Rust's orphan rules. An unprefixed local component marker has different ownership rules, covered by the [`#[default_impl]` reference](/docs/reference/attributes/default_impl).

A namespace's fixed bindings cannot be overridden by joining contexts or inheriting namespaces. Adding a more specific entry does not replace a binding, and a context cannot disable just one fixed default while keeping the rest of that same namespace. Keep choices that should vary on paths the namespace leaves unbound.

### Bind composite providers in the namespace body

A wrapper such as `FilterCensoredUsername<CreateUserWithPostgres>` is a complete provider choice, so record it directly in the namespace body:

```rust
cgp_namespace! {
    DefaultAppComponents {
        @app.core.user.UserCreatorComponent:
            FilterCensoredUsername<CreateUserWithPostgres>,
    }
}
```

The application only needs to choose its filters once the namespace binds the remaining user and post providers. In this example, `ContentFilterComponents` names the AI-backed filter bundle defined earlier:

```rust
type ContentFilterComponents = AiContentFilterComponents;
```

The application selects that bundle explicitly:

```rust
delegate_components! {
    ProductionApp {
        namespace DefaultAppComponents;

        @app.extra.content_filter: ContentFilterComponents,
    }
}
```

Leaving the filter path unbound lets each context choose its filters. A test context can select `DummyContentFilterComponents` at that same path. Both contexts still need component checks, including the dependencies of providers supplied by defaults.

### Choose how much wiring to share

Separate structural routes from fixed provider choices so configurations can reuse the same routes. Put the routes in a base namespace and fixed choices in a configuration namespace that inherits it. Another configuration can then reuse the routes without inheriting provider choices it needs to replace.

Choose a namespace that leaves a destination open when you need to replace its fixed default. For example, join the base `DefaultNamespace` and supply the required bindings there.

`#[default_impl]` is convenient for gradual adoption in a single crate, where the namespace and provider definitions can live together. As providers move into separate crates, namespace-body entries let the namespace's own crate assemble them without requiring registration attributes beside each implementation. The ownership rule still applies to the generated binding.

I see default implementations as a way to move gradually from a single-crate application to a more modular one. Ordinary traits may already be sufficient when a single crate has one implementation of each operation. An application that later needs more modularity can first refactor its monolithic code into CGP components with defaults, without significantly disrupting its organization. It can then introduce explicit bundles and split crates as those needs arise, rather than requiring the full wiring structure at the start.

Choose the amount of wiring that makes the application's decisions clear. Defaults suit choices every joining context should share, while explicit bundles suit interchangeable implementation groups. Smaller applications can stay with direct wiring until grouping makes their configuration easier to read.

## Other improvements

The release also adds smaller features that build on the same machinery. Their references cover the full syntax:

- **Per-type dispatch with `open`:** choose providers for a generic component directly in a context's table, without declaring a namespace or a nested `UseDelegate` table. See [`delegate_components!`](/docs/reference/macros/delegate_components#choosing-a-provider-per-type-the-open-statement).
- **Importing tables with `for`:** bring entries from another namespace table onto a path, so independently defined groups of defaults can be assembled in one context. See [namespace statements](/docs/reference/macros/delegate_components#the-namespace-statements).
- **Implementation-only generics:** `#[impl_generics]` lets a `#[cgp_fn]` implementation infer a generic type from an implicit field without exposing that type as a trait parameter. See [`#[impl_generics]`](/docs/reference/attributes/impl_generics).
- **Readable data shapes:** [`Struct!`](/docs/reference/macros/struct) and [`Enum!`](/docs/reference/macros/enum) express the field lists of structs and enums using declaration-like syntax. cargo-cgp also uses these forms when displaying shapes.
- **Variants without fields:** the extensible-variant derives accept variants such as `Closed`, `Closed()`, and `Closed {}`, representing their payload as `Nil`. A `no_std` crate using the mutable extractor must have `Box` in scope.

The handler macros also generate self-contained expansions without relying on a prelude import at the call site. The release fixes lifetime handling and supertrait support in `#[cgp_auto_dispatch]`, and improves rejection messages for unsupported function signatures in `#[cgp_computer]` and `#[cgp_producer]`.

## Breaking changes and migration

Existing applications need source changes when moving from v0.7.0. The largest change is the removal of presets, which namespaces replace.

### Replace presets with namespace configuration

The preset system described [earlier](#why-the-earlier-grouping-approaches-were-insufficient) is removed in v0.8.0. Its shared provider choices can become namespace bindings, while groups that need to remain interchangeable can become aggregate providers selected through paths.

The following v0.7.0 example defines a preset and inherits it into a context. **This is old syntax and does not compile with v0.8.0:**

```rust
cgp_preset! {
    PostgresUserComponents {
        UserCreatorComponent:
            FilterCensoredUsername<CreateUserWithPostgres>,
        UserGetterComponent: GetUserWithPostgres,
        UserUpdaterComponent: UpdateUserWithPostgres,
    }
}

#[cgp_inherit(PostgresUserComponents)]
pub struct ProductionApp {
    pub database: PostgresDb,
}

delegate_components! {
    ProductionApp {
        // The inherited preset supplies the user-component entries.
        // Other component bindings go here.
    }
}
```

A configuration namespace can preserve the preset's fixed user-provider choices. Register the user components under `@app.core.user` in `DefaultNamespace`, using the `#[prefix(... in DefaultNamespace)]` attributes shown earlier. Then replace the preset with this namespace:

```rust
cgp_namespace! {
    new PostgresAppNamespace: DefaultNamespace {
        @app.core.user.UserCreatorComponent:
            FilterCensoredUsername<CreateUserWithPostgres>,
        @app.core.user.UserGetterComponent: GetUserWithPostgres,
        @app.core.user.UserUpdaterComponent: UpdateUserWithPostgres,
    }
}
```

The migrated context must also supply the censor required by its creation wrapper. Register `UsernameCensor` under `@app.extra.content_filter` in `DefaultNamespace`. With the user components and filter registered, replace the inheritance attribute with explicit delegation on the context:

```rust
#[derive(HasField)]
pub struct ProductionApp {
    pub database: PostgresDb,
}

delegate_components! {
    ProductionApp {
        namespace PostgresAppNamespace;

        @app.extra.content_filter.UsernameCensorComponent: AiUserCensor,
    }
}

check_components! {
    ProductionApp {
        UserCreatorComponent,
        UserGetterComponent,
        UserUpdaterComponent,
        UsernameCensorComponent,
    }
}
```

The example above deliberately checks only the migrated user group and its filter. Add the post operations and any other dependencies your application uses.

An aggregate provider keeps the user-provider group interchangeable. If configurations need that variation, retain `PostgresUserComponents` using `delegate_components! { new PostgresUserComponents { ... } }` and select it with `@app.core.user: PostgresUserComponents`, as in the main walkthrough. Choose between this configurable bundle arrangement and the fixed namespace bindings above according to what should vary.

The removed preset constructs and their replacements are:

| Removed construct | What to use |
| --- | --- |
| `cgp_preset!` | A configuration namespace for shared fixed choices, or an aggregate provider for a selectable group. |
| `#[cgp_inherit]` | A `namespace ...;` statement and explicit path entries inside `delegate_components!`. |
| `#[wrap_provider]` | Explicit aggregate providers and delegation entries. |
| `#[cgp::re_export_imports]` | Ordinary Rust imports for the types used in namespace or delegation tables. |
| `IsPreset` | Remove bounds on the preset marker. Generic code that queries a namespace uses that namespace's generated lookup trait. |

### Update attribute syntax and direct dependencies

The associated-type separator in `#[use_type]` changes from `::` to `.`:

```rust
// v0.7.0
#[use_type(HasErrorType::Error)]

// v0.8.0
#[use_type(HasErrorType.Error)]
```

Equality imports use the new separator too. Write `#[use_type(HasErrorType.{Error = AppError})]`. The [`#[use_type]` reference](/docs/reference/attributes/use_type) covers both ordinary and equality imports.

The extra-feature macro crates are renamed from `cgp-extra-macro` and `cgp-extra-macro-lib` to `cgp-macro-extra` and `cgp-macro-extra-lib`. Update direct dependencies on those crates. Imports through `cgp::prelude` keep their names.

Self-contained handler-macro expansions may leave imports unused. Remove imports the compiler reports when they existed only for the old expansion.

`#[cgp_auto_dispatch]` rejects attribute arguments and typed receivers such as `self: Box<Self>`. It previously ignored the arguments or miscompiled those receivers.

The new `Struct!` and `Enum!` prelude exports can make a macro name ambiguous. Qualify the call if another glob import provides the same name.

### Check error-backend behavior

`cgp-error-eyre` enables eyre's automatic default-handler installation and tracks the caller of `raise_error` and `wrap_error`.

`cgp-error-std` changes how wrapped errors are displayed. Ordinary `Display` prints only the outer detail, while alternate `Display` and `Debug` include the chain. This avoids duplicated sources when a reporter walks `source()` itself. Update output assertions that depend on the old formatting.

The minimum anyhow and eyre dependencies rise to 1.0.104 and 0.6.14 respectively. The backend READMEs in the [CGP repository](https://github.com/contextgeneric/cgp/tree/main/crates/standalone/error) describe their use.

## Try one part of your application

With v0.8.0, I want to make CGP easier to learn and maintain. cargo-cgp helps explain missing dependencies, and the expanded documentation gives readers somewhere to follow those explanations. As an application grows, namespaces let its wiring show which groups of implementations it selects.

CGP still has a learning curve, and the tooling and documentation need further work.

Start with a small example or one part of your existing application. If you already use CGP, try grouping one part of your wiring while keeping its component checks in place. If you are new to CGP, the [Quickstart](/docs/quickstart) provides a smaller starting point.

I would appreciate hearing where you still struggle to trace an implementation, understand a diagnostic, or follow an explanation. Those examples will help me decide what to improve next.
