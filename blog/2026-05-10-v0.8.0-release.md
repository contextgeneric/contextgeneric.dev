# CGP v0.8.0 - cargo-cgp, new documentation, and namespaces

**CGP v0.8.0 is out!** With this release, I want to make CGP easier to learn and maintain. cargo-cgp helps explain wiring errors, and the expanded documentation gives you somewhere to follow up. For growing applications, namespaces let the wiring show which groups of implementations each configuration selects.

<!--truncate-->

Context-Generic Programming (CGP) is a language extension for Rust, with pluggable trait implementations at compile-time. It is an ordinary library on stable Rust: applications select providers through wiring that resolves to static calls. You can adopt it one component at a time. The [Overview](/docs/overview) explains the model.

I'll start with cargo-cgp and the new documentation, then work through namespaces using a social-media application. The namespace walkthrough is the longest part, so you can read the tooling and documentation news on their own if you prefer. ## Diagnosing wiring with cargo-cgp

Since CGP began, verbose and confusing compiler errors have been one of the largest obstacles to adopting it. Forget a field or a component binding, and the compiler can respond with generated traits and type-level encodings of fields or paths. The compiler checks the Rust produced by macro expansion, so its explanation can be far removed from the code where we made the mistake.

For a newcomer, that can mean learning advanced Rust traits and generics, along with CGP's internals, just to diagnose a small mistake. You might understand the program you are trying to write and still have little idea why it does not compile. Better syntax alone cannot address that difficulty.

With [cargo-cgp v0.1.0](/docs/cargo-cgp), I want to make that investigation more approachable. This separate tool checks CGP code and explains missing dependencies in terms of the fields, components, and providers you wrote. It can also show you the generated Rust when you want to look deeper. `cargo cgp check` leads with the root cause for the classes it recognizes, and the tool does not yet reshape every class.

### Find a missing field

Let's try it on a small mistake from the [area-calculation tutorial](/docs/tutorials/area-calculation/static-dispatch). We have an area provider that multiplies `width` by `height`, and a `Rectangle` that supplies only `width`. Here, the rectangle itself is the context: it is the value the operation acts on, and its fields supply the provider's inputs.

Save this library example as `src/lib.rs` in a Cargo package using `cgp = "0.8.0"`:

```rust
use cgp::prelude::*;

#[cgp_component(AreaCalculator)]
pub trait CanCalculateArea {
    fn area(&self) -> f64;
}

#[cgp_impl(new RectangleArea)]
impl AreaCalculator {
    fn area(&self, #[implicit] width: f64, #[implicit] height: f64) -> f64 {
        width * height
    }
}

#[derive(HasField)]
pub struct Rectangle {
    pub width: f64,
    // missing `height` field
}

delegate_and_check_components! {
    Rectangle {
        AreaCalculatorComponent: RectangleArea,
    }
}
```

The table selects `RectangleArea`, whose `#[implicit]` arguments read the rectangle's fields. Because we used `delegate_and_check_components!`, the compiler checks those dependencies at the wiring entry. Run `cargo cgp check`, and it points to the field we forgot:

```text
error[E0277]: [CGP-E001] missing field `height` on `Rectangle`
  --> src/lib.rs:23:9
   |
23 |         AreaCalculatorComponent: RectangleArea,
   |         ^^^^^^^^^^^^^^^^^^^^^^^
   |
   = note: root cause: [CGP-E110] missing field `height` on `Rectangle`
           this is required through the dependency chain:
             [CGP-E101] consumer trait impl `CanCalculateArea` for context `Rectangle`
             └─ [CGP-E102] provider trait impl `AreaCalculator` with context `Rectangle` for provider `RectangleArea`
               └─ [CGP-E110] missing field `height` on `Rectangle`
   = help: add the field `height: f64` to `Rectangle`
```

We can go straight from “missing field `height`” to the suggested change, `height: f64`. If we need to understand why the field matters, the dependency tree traces it back through `RectangleArea` to the area operation. For comparison, plain `cargo check` describes the same mistake through generated traits and a nested `Symbol` type:

Following that suggestion, we add the missing field:

```rust
#[derive(HasField)]
pub struct Rectangle {
    pub width: f64,
    pub height: f64,
}
```

The wiring check now passes, and the provider can read both fields to calculate the area. Fixing the mistake did not require decoding the type-level spelling of `height`.

To produce this explanation, cargo-cgp wraps a nightly compiler and uses the Rust compiler's API to inspect the failed dependencies. It can follow their chain using information that would be difficult to recover from the printed diagnostic alone. That access is why the tool has its own compiler-linked driver.

### Try the checker

With cargo and rustup available, you can install the tool and set up its compiler-linked driver, then check your own project:

```sh
cargo install cargo-cgp
cargo cgp setup
# Run this from your CGP project's directory:
cargo cgp check
```

`cargo cgp setup` installs the tool's pinned nightly and builds the matching driver. That nightly is used for cargo-cgp's checks; your application keeps its normal toolchain for ordinary cargo builds, and CGP itself still compiles on stable Rust. You can use CGP without installing cargo-cgp.

Use plain cargo to build, run, and test applications. cargo-cgp supplies `check` for diagnostics and [`expand`](/docs/cargo-cgp/expand) for reading the Rust generated by macros, with CGP's type-level constructs restored to readable notation. The [installation guide](/docs/cargo-cgp/installation) covers setup, updates, and the Nix alternative.

## Grouping component wiring with namespaces

The new release also introduces new features that solve a major pain point in scaling the number of CGP components, by introducing a new concept called [**namespaces**](/docs/concepts/namespaces). We will explore this in detail next.

When an application has only a few components, writing out its `delegate_components!` table is straightforward. Each time we split behavior into another component, though, we add a routing entry. Eventually, someone opening the application has to sort through a long list of bindings before they can see which ones belong together. The implementations have become more reusable, but the configuration has become harder to follow.

I have tried a few ways to address this difficulty. Provider bundles collect implementations, but applications still have to list the components they forward to each bundle. The earlier preset system reduced some repetition too, with limitations I will return to below.

With [**namespaces**](/docs/concepts/namespaces), we can now give those groups names and select their implementations together. I'll work through a social-media application whose production and test configurations share a PostgreSQL-backed core but use different content filters. By the end, that difference will be visible in one wiring entry.

If you have already maintained a large wiring table, you may prefer to jump to [the namespace syntax](#introducing-cgp-namespaces-and-paths) or [the migration guide](#breaking-changes-and-migration). Otherwise, let's start with the small application and see how its wiring grows.

### Start with a manager per domain {#an-example-social-media-web-app}

Suppose we are building a social-media service that manages users and posts. We need a database handle and a place to choose the implementations the service uses, so our context will represent the application. This is a different role from the earlier `Rectangle`, where the context was the data being operated on.

The snippets illustrate wiring rather than a complete web service. They assume `use cgp::prelude::*;` and omit domain type declarations and database query bodies. The [web-app walkthrough](/docs/projects/cgp-examples/web-app) follows the same example, and its [compiling source](https://github.com/contextgeneric/cgp-examples/tree/v0.8.0/web-app) uses placeholder database operations.

We can begin with a familiar organization: one manager trait for users and another for posts.

```rust
#[cgp_component(UserManager)]
pub trait CanManageUser {
    fn create_user(&self, username: &str, email: &Email) -> Result<User, Error>;

    fn get_user(&self, user_id: &UserId) -> Result<User, Error>;

    fn update_user_data(&self, user_id: &UserId, user_data: &UserData) -> Result<(), Error>;
}

#[cgp_component(PostManager)]
pub trait CanManagePost {
    fn create_post(&self, title: &str, content: &str) -> Result<Post, Error>;

    fn get_post(&self, post_id: &PostId) -> Result<Post, Error>;

    fn update_post(&self, post_id: &PostId, content: &str) -> Result<(), Error>;

    fn delete_post(&self, post_id: &PostId) -> Result<(), Error>;
}
```

The methods describe what the service can do. Adding `#[cgp_component]` lets us write their implementations separately from the application that uses them: it generates a provider trait such as `UserManager` and a wiring key such as `UserManagerComponent`. The application will choose a provider through that key.

Choosing a manager provider chooses all its methods together. That is our design for this first version: a component can contain multiple methods, associated types, and constants, just like an ordinary trait. As the service grows, we will see where choosing those methods together becomes inconvenient.

For the PostgreSQL implementations, each method declares the database handle it needs as an implicit argument. The providers can then work with any application supplying that dependency:

```rust
#[cgp_impl(new PostgresUserManager)]
impl UserManager {
    fn create_user(
        &self,
        #[implicit] database: &PostgresDb,
        username: &str,
        email: &Email,
    ) -> Result<User, Error> {
        // ...
    }

    fn get_user(
        &self,
        #[implicit] database: &PostgresDb,
        user_id: &UserId,
    ) -> Result<User, Error> {
        // ...
    }

    fn update_user_data(
        &self,
        #[implicit] database: &PostgresDb,
        user_id: &UserId,
        user_data: &UserData,
    ) -> Result<(), Error> {
        // ...
    }
}

#[cgp_impl(new PostgresPostManager)]
impl PostManager {
    fn create_post(
        &self,
        #[implicit] database: &PostgresDb,
        title: &str,
        content: &str,
    ) -> Result<Post, Error> {
        // ...
    }

    fn get_post(
        &self,
        #[implicit] database: &PostgresDb,
        post_id: &PostId,
    ) -> Result<Post, Error> {
        // ...
    }

    fn update_post(
        &self,
        #[implicit] database: &PostgresDb,
        post_id: &PostId,
        content: &str,
    ) -> Result<(), Error> {
        // ...
    }

    fn delete_post(
        &self,
        #[implicit] database: &PostgresDb,
        post_id: &PostId,
    ) -> Result<(), Error> {
        // ...
    }
}
```

Any context with the required PostgreSQL `database` field can reuse these providers. If we wanted a SQLite-backed application, we could write `SqliteUserManager` and `SqlitePostManager` against the same interfaces and select those instead.

For our production application, we supply the database field and choose the PostgreSQL managers:

```rust
#[derive(HasField)]
pub struct ProductionApp {
    pub database: PostgresDb,
}

delegate_and_check_components! {
    ProductionApp {
        UserManagerComponent: PostgresUserManager,
        PostManagerComponent: PostgresPostManager,
    }
}
```

Both managers share one dependency: the database field that `#[derive(HasField)]` makes available to their implicit arguments. The combined delegation-and-check macro verifies that `ProductionApp` can use the selected providers. For now, those two entries cover all the user and post operations.

### Add dependencies as the service grows

Now suppose the service needs to reject censored usernames and spam posts. Before inserting a user or a post, its manager must consult a filter. We can add a component for each check and declare the manager's dependency on its consumer trait with `#[uses]`:

```rust
#[cgp_component(UsernameCensor)]
pub trait CanCensorUsername {
    fn username_is_censored(&self, username: &str) -> Probability;
}

#[cgp_component(SpamMessageDetector)]
pub trait CanDetectSpamMessage {
    fn message_is_spam(&self, message: &str) -> Probability;
}

#[cgp_impl(new PostgresUserManager)]
#[uses(CanCensorUsername)]
impl UserManager {
    fn create_user(
        &self,
        #[implicit] database: &PostgresDb,
        username: &str,
        email: &Email,
    ) -> Result<User, Error> {
        if self.username_is_censored(username) > Probability::new(0.8) {
            return Err(Error::InvalidUsername);
        }

        // ...
    }

    // ...
}

#[cgp_impl(new PostgresPostManager)]
#[uses(CanDetectSpamMessage)]
impl PostManager {
    fn create_post(
        &self,
        #[implicit] database: &PostgresDb,
        title: &str,
        content: &str,
    ) -> Result<Post, Error> {
        if self.message_is_spam(content) > Probability::new(0.8) {
            return Err(Error::InvalidMessage);
        }

        // ...
    }

    // ...
}
```

Each manager compares its filter's score with a rejection threshold before writing to the database. The `#[uses]` attribute declares the new trait dependency; `#[implicit] database` still supplies the database handle. The remaining manager methods are omitted here.

In production, filtering might involve an AI model or a cloud service. We would rather not make those calls every time we test the rest of the application. A deterministic string-matching filter lets tests run more quickly while keeping the same PostgreSQL managers:

```rust
#[derive(HasField)]
pub struct ProductionApp {
    pub database: PostgresDb,
    // ... // AI client credentials
}

delegate_and_check_components! {
    ProductionApp {
        UserManagerComponent: PostgresUserManager,
        PostManagerComponent: PostgresPostManager,
        UsernameCensorComponent: AiUserCensor,
        SpamMessageDetectorComponent: AiSpamMessageDetector,
    }
}

#[derive(HasField)]
pub struct TestApp {
    pub database: PostgresDb,
}

delegate_and_check_components! {
    TestApp {
        UserManagerComponent: PostgresUserManager,
        PostManagerComponent: PostgresPostManager,
        UsernameCensorComponent: DummyUserCensor,
        SpamMessageDetectorComponent: DummySpamMessageDetector,
    }
}
```

Both contexts supply the database field and select the same managers. Only the filter entries differ, so tests can exercise the database implementations with deterministic filtering.

The wiring has grown along with the dependency tree. Four component entries on each context already means eight entries to maintain, even in this small service.

### Split independently reusable operations {#fine-grained-traits}

Adding `CanCensorUsername` to the user manager looked straightforward. But that bound belongs to the whole `PostgresUserManager` implementation, so even `get_user` now requires a context with a censor. Retrieving a user never runs the filter; the dependency arrives because retrieval and creation share a provider. The post manager has the same problem with spam detection, and every unrelated dependency we add makes the managers harder to maintain and test.

As we add operations, the domain boundaries become less obvious too. `get_user_profile_picture` might fit in the user manager, but it could need an entirely different set of dependencies. `get_user_posts` concerns both users and posts. Naming a manager after an entity does not settle which operations are useful to group together.

There is also a reason to keep the caller's interface narrow. If we later add `delete_user` to the manager, generic code that only retrieves users would depend on an interface that includes deletion. Giving retrieval its own trait lets that code request exactly the operation it needs.

Splitting the managers into smaller components lets each provider declare only the dependencies it uses. For the user operations, that gives us:

```rust
#[cgp_component(UserCreator)]
pub trait CanCreateUser {
    fn create_user(&self, username: &str, email: &Email) -> Result<User, Error>;
}

#[cgp_component(UserGetter)]
pub trait CanGetUser {
    fn get_user(&self, user_id: &UserId) -> Result<User, Error>;
}

#[cgp_component(UserUpdater)]
pub trait CanUpdateUser {
    fn update_user_data(&self, user_id: &UserId, user_data: &UserData) -> Result<(), Error>;
}
```

The user-creation provider needs the censor, while the getter needs only the database:

```rust
#[cgp_impl(new CreateUserWithPostgres)]
#[uses(CanCensorUsername)]
impl UserCreator {
    fn create_user(
        &self,
        #[implicit] database: &PostgresDb,
        username: &str,
        email: &Email,
    ) -> Result<User, Error> {
        if self.username_is_censored(username) > Probability::new(0.8) {
            return Err(Error::InvalidUsername);
        }

        // ...
    }
}

#[cgp_impl(new GetUserWithPostgres)]
impl UserGetter {
    fn get_user(&self, #[implicit] database: &PostgresDb, user_id: &UserId) -> Result<User, Error> {
        // ...
    }
}
```

`GetUserWithPostgres` can be used with a database alone, while `CreateUserWithPostgres` keeps its censor dependency. A caller bounded by `CanGetUser` can retrieve users without depending on creation or deletion. The same split gives us separate post-creation, retrieval, update, and deletion components.

### Separate filtering from database access

The username check does not depend on PostgreSQL at all. Now that creation has its own component, we can move the check into a wrapper and apply it to whichever user-creation provider we choose:

```rust
#[cgp_impl(new FilterCensoredUsername<InnerCreator>)]
#[uses(CanCensorUsername)]
#[use_provider(InnerCreator: UserCreator)]
impl<InnerCreator> UserCreator {
    fn create_user(&self, username: &str, email: &Email) -> Result<User, Error> {
        if self.username_is_censored(username) > Probability::new(0.8) {
            return Err(Error::InvalidUsername);
        }

        InnerCreator::create_user(self, username, email)
    }
}

#[cgp_impl(new CreateUserWithPostgres)]
impl UserCreator {
    fn create_user(
        &self,
        #[implicit] database: &PostgresDb,
        username: &str,
        email: &Email,
    ) -> Result<User, Error> {
        // ...
    }
}
```

The wrapper rejects censored names, then hands an allowed request to `InnerCreator::create_user`. Its `#[use_provider]` attribute requires that inner provider to support user creation for the same context. Because it takes another provider as a parameter, we call `FilterCensoredUsername` a [**higher-order provider**](/docs/concepts/higher-order-providers).

`CreateUserWithPostgres` can now focus on constructing the SQL insert query. When wiring the application, we can select it directly or add filtering with `FilterCensoredUsername<CreateUserWithPostgres>`. A local-first application could instead select `FilterCensoredUsername<CreateUserWithSqlite>` and reuse the same filter. Changing the database would not require copying the username check.

`FilterSpamMessage<InnerCreator>` applies the same separation to post creation. It uses `CanDetectSpamMessage` to reject spam, then forwards an allowed post to its inner `PostCreator`. The wiring can therefore choose `FilterSpamMessage<CreatePostWithPostgres>` independently of the database provider's implementation.

### Count the cost of the separation

With dependencies isolated and filters reusable, the individual providers are easier to work with. The production wiring, however, now has to select seven CRUD operations and two filters:

```rust
delegate_components! {
    ProductionApp {
        UserCreatorComponent:
            FilterCensoredUsername<CreateUserWithPostgres>,
        UserGetterComponent:
            GetUserWithPostgres,
        UserUpdaterComponent:
            UpdateUserWithPostgres,
        PostCreatorComponent:
            FilterSpamMessage<CreatePostWithPostgres>,
        PostGetterComponent:
            GetPostWithPostgres,
        PostUpdaterComponent:
            UpdatePostWithPostgres,
        PostDeleterComponent:
            DeletePostWithPostgres,
        UsernameCensorComponent:
            AiUserCensor,
        SpamMessageDetectorComponent:
            AiSpamMessageDetector,
    }
}
```

Our small example has gone from four component entries to nine. With more features, an application can reach dozens or hundreds. Each binding has a purpose, but the flat list gives a reader little help in finding which choices belong together.

We can make the list easier to read by collecting the user bindings into their own provider bundle:

```rust
delegate_components! {
    new PostgresUserComponents {
        UserCreatorComponent:
            FilterCensoredUsername<CreateUserWithPostgres>,
        UserGetterComponent:
            GetUserWithPostgres,
        UserUpdaterComponent:
            UpdateUserWithPostgres,
    }
}
```

With `new PostgresUserComponents`, we declare an [**aggregate provider**](/docs/concepts/aggregate-providers): its table delegates each operation to another provider. A reader can examine the user wiring on its own, without the post operations and filters alongside it. We can collect those into `PostgresPostComponents` and `AiContentFilterComponents` in the same way.

Back in the application, we forward the components to their bundles using [array keys](/docs/reference/macros/delegate_components#the-key-forms):

```rust
delegate_components! {
    ProductionApp {
        [
            UserCreatorComponent,
            UserGetterComponent,
            UserUpdaterComponent,
        ]:
            PostgresUserComponents,
        [
            PostCreatorComponent,
            PostGetterComponent,
            PostUpdaterComponent,
            PostDeleterComponent,
        ]:
            PostgresPostComponents,
        [
            UsernameCensorComponent,
            SpamMessageDetectorComponent,
        ]:
            AiContentFilterComponents,
    }
}
```

The implementations are grouped, yet we still have to spell out every component name here. Adding a user operation means updating the user bundle and then finding every application that lists its keys. We cannot simply tell the application to use `PostgresUserComponents` for “all user components.” The group itself needs a name we can wire.

### Why the earlier grouping approaches were insufficient

Ideally, the configuration would say something like this, with a key for each group:

```text
delegate_components! {
    ProductionApp {
        ???: // all user components
            PostgresUserComponents,
        ???: // all post components
            PostgresPostComponents,
        ???: // all content filter components
            AiContentFilterComponents,
    }
}
```

The missing keys are the difficulty. Rust's trait system does not provide an operation that expands a type-level list into a separate implementation for every listed key. To express this configuration, CGP needs to handle the groups through its own lookup rules or macro expansion.

One possibility would be a helper macro that supplied the list of keys for each group. That would let us write a hypothetical table like this:

```text
delegate_components! {
    ProductionApp {
        all_user_components!():
            PostgresUserComponents,
        all_post_components!():
            PostgresPostComponents,
        all_content_filter_components!():
            AiContentFilterComponents,
    }
}
```

Here, `all_user_components!()` would expand to `[UserCreatorComponent, UserGetterComponent, UserUpdaterComponent]`, with corresponding lists for posts and filters. Like the `???` keys above, these helpers are pseudocode rather than supported syntax.

Unfortunately, `delegate_components!` receives the literal `all_user_components!()` before the helper expands. When the outer macro parses the table, the component list is not available yet. Supporting this arrangement would require a different macro-composition mechanism, along with a way to generate and export helpers whose names and imports remain usable across crate boundaries.

My earlier [preset system](/blog/hypershell-release#cgp-presets) shared wiring but made independent groups difficult to combine. Its inheritance mechanism could supply one preset to a context, while Rust's coherence restrictions prevented a context from inheriting independent user and post presets that way. I also experimented with macro-based composition of multiple presets, but expansion order and the handling of imports and aliases made that approach tedious to use.

Those attempts helped clarify what I wanted from the feature: an application should be able to name a group and choose its implementation bundle without enumerating every key. In v0.8.0, namespaces express that choice through trait resolution and paths. Existing preset users can find the conversion in the [migration section](#replace-presets-with-namespace-configuration).

### Give component groups a path {#introducing-cgp-namespaces-and-paths}

We can now replace the `???` keys with paths that name the user, post, and content-filter groups. With the component prefixes registered, our application table becomes:

```rust
delegate_components! {
    ProductionApp {
        namespace DefaultNamespace;

        @app.core.user: PostgresUserComponents,
        @app.core.post: PostgresPostComponents,
        @app.extra.content_filter: AiContentFilterComponents,
    }
}
```

The `namespace DefaultNamespace;` statement opts this table into the namespace's registered routes, and each path entry selects a whole bundle. Adding another user operation to the user group no longer requires repeating its component name here. The individual bindings still live in the bundles; the application selects the groups it uses.

To make this work, we give each component a prefix using `#[prefix]`. For `CanCreateUser`, we register `@app.core.user` in the built-in `DefaultNamespace`:

```rust
#[cgp_component(UserCreator)]
#[prefix(@app.core.user in DefaultNamespace)]
pub trait CanCreateUser {
    fn create_user(&self, username: &str, email: &Email) -> Result<User, Error>;
}
```

CGP appends the component marker to this prefix. Once a context joins the namespace, a lookup for `UserCreatorComponent` follows the route to `@app.core.user.UserCreatorComponent`.

The getter and updater belong to that group too, so we register them under the same prefix. For the getter, that means:

```rust
#[cgp_component(UserGetter)]
#[prefix(@app.core.user in DefaultNamespace)]
pub trait CanGetUser {
    fn get_user(&self, user_id: &UserId) -> Result<User, Error>;
}
```

Post operations get their own `@app.core.post` prefix:

```rust
#[cgp_component(PostCreator)]
#[prefix(@app.core.post in DefaultNamespace)]
pub trait CanCreatePost {
    fn create_post(&self, title: &str, content: &str) -> Result<Post, Error>;
}
```

Finally, the filter components register under `@app.extra.content_filter`, also in `DefaultNamespace`. These registrations describe the groups independently of the providers an application chooses.

### Group paths hierarchically

Production and tests both use the PostgreSQL user and post operations. Rather than select those bundles separately in each application, we can collect them under their shared parent, `@app.core`. The paths are hierarchical: `@app.core.user` sits under `@app.core`, which sits under `@app`. An intermediate bundle can therefore gather the core operations, while another gathers the extras:

```rust
delegate_components! {
    new PostgresCoreComponents {
        namespace DefaultNamespace;

        @app.core.user: PostgresUserComponents,
        @app.core.post: PostgresPostComponents,
        // other core components
    }
}

delegate_components! {
    new ProductionExtraComponents {
        namespace DefaultNamespace;

        @app.extra.content_filter: AiContentFilterComponents,
        // other extra components
    }
}
```

Notice that these intermediate bundles also join `DefaultNamespace`. When a lookup reaches a bundle, it receives the bare component key; the namespace statement redirects that key to the paths in the bundle's own table. Our earlier leaf bundles use bare component names already, so they do not need that statement.

The production configuration now selects two groups:

```rust
delegate_components! {
    ProductionApp {
        namespace DefaultNamespace;

        @app.core: PostgresCoreComponents,
        @app.extra: ProductionExtraComponents,
    }
}
```

For testing, the core stays the same. Only the extras entry changes, selecting `DummyExtraComponents` for deterministic filtering:

```rust {6}
delegate_components! {
    TestApp {
        namespace DefaultNamespace;

        @app.core: PostgresCoreComponents,
        @app.extra: DummyExtraComponents,
    }
}
```

For a local configuration, we could make the other choice: keep the production filters and select a SQLite-backed core:

```rust {5}
delegate_components! {
    LocalApp {
        namespace DefaultNamespace;

        @app.core: SqliteCoreComponents,
        @app.extra: ProductionExtraComponents,
    }
}
```

In each case, one entry tells us how the configuration differs from production. `TestApp` changes the extras; `LocalApp` changes the core. With flat tables, we would have to compare the individual component entries, perhaps written in different orders, to reach the same conclusion. We can now read those decisions directly from the wiring.

The selected providers still need their dependencies. Each context must supply the required fields and other traits, and the hypothetical SQLite core would need its corresponding database handle.

### Check the completed configuration

We have organized the provider choices, but we still need to verify that they work together. Wiring is lazy: a `delegate_components!` block can compile before an operation forces the provider dependencies to be checked. A separate check on the concrete application makes that verification explicit:

```rust
check_components! {
    ProductionApp {
        UserCreatorComponent,
        UserGetterComponent,
        UserUpdaterComponent,
        PostCreatorComponent,
        PostGetterComponent,
        PostUpdaterComponent,
        PostDeleterComponent,
        UsernameCensorComponent,
        SpamMessageDetectorComponent,
    }
}
```

Apply the same nine-component check to `TestApp` and any local variant. Earlier stages need checks matching their components: before splitting the managers, for example, check `UserManagerComponent` and `PostManagerComponent`.

The list still names the individual operations we expect to work, even though the routing is grouped. Check them through the real application context that supplies their dependencies. An aggregate provider is a bundle of implementations, and checking it as though it were the application would ask it to supply dependencies that belong on the context.

The [namespace documentation](/docs/concepts/namespaces) explains the lookup model, and the [`delegate_components!` reference](/docs/reference/macros/delegate_components) covers the path syntax.

## Sharing default implementations {#default-implementations}

So far, we have organized the wiring around choices we might want to change: PostgreSQL or SQLite, production or test filters. Bundles work well for that arrangement. We could add a `PostgresWithLoggingCoreComponents` variant, for example, and select the logging-backed core in the same place.

But an application starting out with PostgreSQL may have little reason to define interchangeable database bundles yet. If several contexts should always use the same user and post implementations, making each one select those bundles adds organization without expressing a useful difference. We can instead record those choices once in a namespace and leave only the varying parts to each context. These are **default implementations**.

I see defaults as a way to adopt CGP gradually. Ordinary traits may already be enough for a single-crate application with one implementation of each operation. If that application later needs more modularity, it can move code into CGP components and record its initial provider choices as defaults. Bundles can follow when there are useful groups to swap.

Let's keep the routes we already registered in `DefaultNamespace` and define a configuration namespace that inherits them using the new [`cgp_namespace!`](/docs/reference/macros/cgp_namespace) macro:

```rust
cgp_namespace! {
    new DefaultAppComponents: DefaultNamespace
}
```

`DefaultAppComponents` starts with the prefixes and any default bindings supplied by its parent. We can add our application-specific choices here without changing what other namespaces select. Every context that joins this configuration namespace will share those choices.

For a simple provider, we can place its binding beside its implementation. Add [`#[default_impl]`](/docs/reference/attributes/default_impl) to our earlier `GetUserWithPostgres` definition:

```rust
#[cgp_impl(new GetUserWithPostgres)]
#[default_impl(@app.core.user.UserGetterComponent in DefaultAppComponents)]
impl UserGetter {
    fn get_user(&self, #[implicit] database: &PostgresDb, user_id: &UserId) -> Result<User, Error> {
        // ... query the database
    }
}
```

The implementation now declares that `DefaultAppComponents` uses it at `@app.core.user.UserGetterComponent`. If we prefer to collect the bindings in one place, we can write the same choice in the namespace body instead:

```rust
cgp_namespace! {
    DefaultAppComponents {
        @app.core.user.UserGetterComponent: GetUserWithPostgres,
    }
}
```

These are alternative ways to register the same binding; writing both would create a conflict. The namespace body looks like a [`delegate_components!`](/docs/reference/macros/delegate_components) table, but its choices apply to every context that joins the namespace. We use the full path because the inherited route already maps the bare component marker to that address.

These defaults are fixed choices. Once the namespace binds a provider, a joining context or inheriting namespace cannot override it, even with a more specific entry. A context also cannot disable just one default while retaining the rest of that namespace. Choices that need to vary must stay on destinations the namespace leaves unbound.

There is also a constraint on where we write the registration. With a prefixed path, the binding must live in the crate that owns the namespace, here `DefaultAppComponents`. The path expands to CGP's `PathCons` type, and owning a component marker nested inside that type does not satisfy Rust's [orphan rules](/docs/concepts/coherence). An unprefixed local component marker has different ownership rules, covered by the [`#[default_impl]` reference](/docs/reference/attributes/default_impl).

### Bind composite providers in the namespace body

`FilterCensoredUsername` is generic over its inner provider. For this configuration, we want to choose both the wrapper and its PostgreSQL implementation. We can assemble that complete provider choice directly in the namespace body:

```rust
cgp_namespace! {
    DefaultAppComponents {
        @app.core.user.UserCreatorComponent:
            FilterCensoredUsername<CreateUserWithPostgres>,
    }
}
```

After we bind the remaining user and post providers in the same way, the application only needs to choose its filters. For this example, our production wiring then becomes:

```rust
delegate_components! {
    ProductionApp {
        namespace DefaultAppComponents;

        @app.extra.content_filter: AiContentFilterComponents,
    }
}
```

All the shared user and post choices come from `DefaultAppComponents`. We deliberately left the filter path unbound, so a test context can select `DummyContentFilterComponents` there instead.

### Choose how much wiring to share

Keeping the prefixes in `DefaultNamespace` and the provider choices in `DefaultAppComponents` gives us a useful separation. Another configuration can reuse the same routes without inheriting PostgreSQL choices it needs to replace. That is why the structural routes belong in a base namespace and fixed choices in a configuration namespace that inherits it.

If we later need to replace one of these fixed defaults, we choose a namespace that leaves its destination open. We could return to the base `DefaultNamespace` and supply the required bindings explicitly, as in the earlier bundle examples.

While the application lives in one crate, `#[default_impl]` is a convenient way to keep a binding beside the implementation. As providers move into separate crates, we can move their bindings into the configuration namespace's body. Its own crate then assembles the providers, respecting the same ownership rule without requiring registration attributes beside each implementation.

There is room to start with direct wiring, share fixed choices through defaults, and introduce interchangeable bundles as the application needs them. I would choose whichever arrangement makes the current decisions easiest to see, rather than build the full hierarchy in anticipation of future growth.

## Other improvements

Namespaces are the largest change, but several smaller additions also reduce the work of writing and reading CGP. You can use these without following the full application refactoring above:

- **Choose a provider per type with `open`.** If a generic component needs one provider for a rectangle and another for a circle, you can put those selections directly in the context's table. You do not need to declare a namespace or a nested `UseDelegate` table. The [`delegate_components!` reference](/docs/reference/macros/delegate_components#choosing-a-provider-per-type-the-open-statement) shows the syntax.
- **Assemble separate tables with `for`.** A backend and an API surface may each have their own table of defaults. You can bring entries from another namespace table onto a path in your context, keeping those concerns independently defined. See [namespace statements](/docs/reference/macros/delegate_components#the-namespace-statements).
- **Keep implementation details out of trait parameters.** Sometimes a `#[cgp_fn]` body needs a generic type only because it reads a field of that type. With [`#[impl_generics]`](/docs/reference/attributes/impl_generics), the implementation can infer the type from the implicit field without adding a parameter to the generated trait.
- **Write data shapes as declarations.** A field list is easier to recognize when it looks like the struct or enum it describes. [`Struct!`](/docs/reference/macros/struct) and [`Enum!`](/docs/reference/macros/enum) provide that notation, and cargo-cgp uses it when displaying shapes too.
- **Use fieldless variants directly.** If an enum contains a state such as `Closed`, you can now use the extensible-variant derives without giving it a placeholder payload. The derives accept `Closed`, `Closed()`, and `Closed {}`, representing the payload as `Nil`. A `no_std` crate using the mutable extractor must have `Box` in scope.

There are also fixes for code that previously ran into the limits of the handler macros. Their generated code is now self-contained, so using them does not rely on a prelude import at the call site. `#[cgp_auto_dispatch]` has fixes for lifetime handling and supertrait support, while `#[cgp_computer]` and `#[cgp_producer]` give clearer rejection messages for unsupported function signatures.

## Breaking changes and migration

Existing applications need source changes when moving from v0.7.0. The largest change is the removal of presets, which namespaces replace.

### Replace presets with namespace configuration

The preset system described [earlier](#why-the-earlier-grouping-approaches-were-insufficient) is removed in v0.8.0. Its shared provider choices can become namespace bindings, while groups that need to remain interchangeable can become aggregate providers selected through paths.

The following v0.7.0 example defines a preset and inherits it into a context. **This is old syntax and does not compile with v0.8.0:**

```rust
cgp_preset! {
    PostgresUserComponents {
        UserCreatorComponent:
            FilterCensoredUsername<CreateUserWithPostgres>,
        UserGetterComponent: GetUserWithPostgres,
        UserUpdaterComponent: UpdateUserWithPostgres,
    }
}

#[cgp_inherit(PostgresUserComponents)]
pub struct ProductionApp {
    pub database: PostgresDb,
}

delegate_components! {
    ProductionApp {
        // The inherited preset supplies the user-component entries.
        // Other component bindings go here.
    }
}
```

A configuration namespace can preserve the preset's fixed user-provider choices. Register the user components under `@app.core.user` in `DefaultNamespace`, using the `#[prefix(... in DefaultNamespace)]` attributes shown earlier. Then replace the preset with this namespace:

```rust
cgp_namespace! {
    new PostgresAppNamespace: DefaultNamespace {
        @app.core.user.UserCreatorComponent:
            FilterCensoredUsername<CreateUserWithPostgres>,
        @app.core.user.UserGetterComponent: GetUserWithPostgres,
        @app.core.user.UserUpdaterComponent: UpdateUserWithPostgres,
    }
}
```

The migrated context must also supply the censor required by its creation wrapper. Register `UsernameCensor` under `@app.extra.content_filter` in `DefaultNamespace`. With the user components and filter registered, replace the inheritance attribute with explicit delegation on the context:

```rust
#[derive(HasField)]
pub struct ProductionApp {
    pub database: PostgresDb,
}

delegate_components! {
    ProductionApp {
        namespace PostgresAppNamespace;

        @app.extra.content_filter.UsernameCensorComponent: AiUserCensor,
    }
}

check_components! {
    ProductionApp {
        UserCreatorComponent,
        UserGetterComponent,
        UserUpdaterComponent,
        UsernameCensorComponent,
    }
}
```

The example above deliberately checks only the migrated user group and its filter. Add the post operations and any other dependencies your application uses.

An aggregate provider keeps the user-provider group interchangeable. If configurations need that variation, retain `PostgresUserComponents` using `delegate_components! { new PostgresUserComponents { ... } }` and select it with `@app.core.user: PostgresUserComponents`, as in the main walkthrough. Choose between this configurable bundle arrangement and the fixed namespace bindings above according to what should vary.

The removed preset constructs and their replacements are:

| Removed construct | What to use |
| --- | --- |
| `cgp_preset!` | A configuration namespace for shared fixed choices, or an aggregate provider for a selectable group. |
| `#[cgp_inherit]` | A `namespace ...;` statement and explicit path entries inside `delegate_components!`. |
| `#[wrap_provider]` | Explicit aggregate providers and delegation entries. |
| `#[cgp::re_export_imports]` | Ordinary Rust imports for the types used in namespace or delegation tables. |
| `IsPreset` | Remove bounds on the preset marker. Generic code that queries a namespace uses that namespace's generated lookup trait. |

### Update attribute syntax and direct dependencies

The associated-type separator in `#[use_type]` changes from `::` to `.`:

```rust
// v0.7.0
#[use_type(HasErrorType::Error)]

// v0.8.0
#[use_type(HasErrorType.Error)]
```

Equality imports use the new separator too. Write `#[use_type(HasErrorType.{Error = AppError})]`. The [`#[use_type]` reference](/docs/reference/attributes/use_type) covers both ordinary and equality imports.

The extra-feature macro crates are renamed from `cgp-extra-macro` and `cgp-extra-macro-lib` to `cgp-macro-extra` and `cgp-macro-extra-lib`. Update direct dependencies on those crates. Imports through `cgp::prelude` keep their names.

Self-contained handler-macro expansions may leave imports unused. Remove imports the compiler reports when they existed only for the old expansion.

`#[cgp_auto_dispatch]` rejects attribute arguments and typed receivers such as `self: Box<Self>`. It previously ignored the arguments or miscompiled those receivers.

The new `Struct!` and `Enum!` prelude exports can make a macro name ambiguous. Qualify the call if another glob import provides the same name.

### Check error-backend behavior

`cgp-error-eyre` enables eyre's automatic default-handler installation and tracks the caller of `raise_error` and `wrap_error`.

`cgp-error-std` changes how wrapped errors are displayed. Ordinary `Display` prints only the outer detail, while alternate `Display` and `Debug` include the chain. This avoids duplicated sources when a reporter walks `source()` itself. Update output assertions that depend on the old formatting.

The minimum anyhow and eyre dependencies rise to 1.0.104 and 0.6.14 respectively. The backend READMEs in the [CGP repository](https://github.com/contextgeneric/cgp/tree/main/crates/standalone/error) describe their use.

## Try one part of your application

We started with two manager choices and ended with applications that could share a core, change their filters, or use a different database. Namespaces let the top-level wiring express those choices even as we split the implementations into smaller pieces. I hope that makes similar refactorings easier to follow in your own projects, with cargo-cgp and the new documentation there to help when something is unclear.

There is still a learning curve, and both the tooling and documentation need further work. You do not need to adopt the whole arrangement in this post to find out whether one part helps.

Start with a small example or one part of your existing application. If you already use CGP, try grouping one part of your wiring while keeping its component checks in place. If you are new to CGP, the [Quickstart](/docs/quickstart) provides a smaller starting point.

I would appreciate hearing where you still struggle to trace an implementation, understand a diagnostic, or follow an explanation. Those examples will help me decide what to improve next. You can share them in [GitHub Discussions](https://github.com/orgs/contextgeneric/discussions). Thank you for reading and trying CGP.
