# `Product!` & `product!`

A type-level list and its value-level counterpart.

## Overview

`Product![A, B, C]` represents an ordered sequence of types as a single type. CGP uses it to describe the
*shape* of a struct: the list of its fields, in order, as one type that generic code can reason about.

It is sometimes called an anonymous product type, because like a tuple it holds several things at once. The
difference from a tuple is the one that matters: a `Product!` is built from a recursive spine that generic code
can take apart **one element at a time**:

```rust
Product![u32, String, bool]
```

That recursion makes structural, field-by-field operations possible at all. Because a struct's fields
are exposed as a single list type through [`HasFields`](../traits/has_fields.md), a provider can be written
once to walk, transform, or rebuild *any* struct's fields without naming the concrete struct, by recursing
over the list. A plain tuple cannot be decomposed that way in generic code; the recursive list can.

The lowercase `product![a, b, c]` is the value-level half. `Product!` produces a *type* and is used in type
position (associated types, bounds, aliases), while `product!` produces a *value* of the matching type and is
used in expression position, mirroring Rust's own split between a struct type and a struct literal.

**You mostly read these rather than write them.** A struct's field list is generated by
[`#[derive(HasFields)]`](../derives/derive_has_fields.md); you write `Product!` by hand in a handler
pipeline, listing the steps to run in order.

## Usage

Both macros take a comma-separated list, which may be empty, and a trailing comma is allowed:

```rust
Product![u32, String, bool]              // a type
product![1u32, "hi".to_string(), true]   // a value of that type
Product![]                               // the empty list type
```

The element lists line up positionally, so the value `product!` builds has exactly the type `Product!` builds
over the corresponding element types.

`Product!` is used wherever a type is expected and `product!` wherever a value is expected. Nothing else about
them varies: there are no options and no attributes.

## Examples

The commonest appearance by far is the field list a struct derives, where each element pairs a field name with
its type:

```rust
use cgp::prelude::*;

#[derive(HasFields)]
pub struct Person {
    pub name: String,
    pub age: u8,
}

// generated:
// impl HasFields for Person {
//     type Fields = Product![
//         Field<Symbol!("name"), String>,
//         Field<Symbol!("age"), u8>,
//     ];
// }
```

The names are [`Symbol!`](./symbol.md) type-level strings and each entry is a [`Field`](../types/field.md), so
the whole `Product!` is a complete type-level description of `Person`'s layout. Generic code walks that list to
build or read a `Person` without being written against `Person`.

You write `Product!` yourself in a handler pipeline, where the list *is* the program: the steps run
left to right:

```rust
delegate_components! {
    MyContext {
        ComputerComponent:
            PipeHandlers<Product![
                Multiply<Symbol!("foo")>,
                Add<Symbol!("bar")>,
                Multiply<Symbol!("baz")>,
            ]>,
    }
}
```

A standalone list and a matching value can also be written directly, which is mostly useful for illustration:

```rust
type Row = Product![u32, String, bool];
let row: Row = product![1, "hi".to_string(), true];
```

## When to reach for it, and when not

**Write `Product!` when a construct asks for a type-level list**, which in practice means a handler pipeline or
a provider list. Everywhere else it is generated for you.

- **Never hand-write the spine.** `Product!` expands to `Cons<A, Cons<B, Nil>>`, and writing it out is
  strictly worse: longer, harder to change, and identical in meaning. The same holds for
  [`Sum!`](./sum.md)'s spine.
- **Use [`#[derive(HasFields)]`](../derives/derive_has_fields.md) for a struct's shape** rather than declaring
  the list yourself. Writing it by hand means restating the struct, and the two will disagree eventually.
- **Use a tuple when nothing generic consumes it.** A `Product!` earns its keep only where code recurses over
  the list; for a fixed group of values passed between known functions, a tuple or a struct is clearer and
  needs no machinery.
- **Use [`Sum!`](./sum.md) for a choice rather than a collection.** `Product!` holds a value for *every*
  element; `Sum!` holds one for exactly *one*. They are duals, and mixing them up produces a type error rather
  than a subtle bug.

## Under the hood

:::note

### Advanced

This section shows the spine both macros build. You do not need it to use them, but a compiler error prints
the expanded form, so recognizing it makes those errors readable. `cargo cgp expand` resugars it
back for your own code.

:::

`Product!` expands to a right-nested chain of `Cons`, terminated by `Nil`:

```rust
// before
Product![A, B, C]

// after
Cons<A, Cons<B, Cons<C, Nil>>>
```

Both building blocks are ordinary types. `Cons<Head, Tail>` is a tuple struct holding the first element and the
rest of the list (`Cons<Head, Tail>(pub Head, pub Tail)`), and `Nil` is a unit struct terminating it. Chaining
through the tail gives a list of any length, and the empty `Product![]` is simply `Nil`. The macro builds the
chain by folding the elements right to left onto `Nil`.

`product!` folds identically but produces a value, using `Cons`'s tuple-struct constructor:

```rust
// before
product![a, b, c]

// after
Cons(a, Cons(b, Cons(c, Nil)))
```

Because `Cons` is a real struct and `Nil` a real unit struct, the result is an ordinary owned value whose type
exactly matches what `Product!` builds over the same elements' types. There is no magic layer between the two
macros: they are the same fold at two levels.

**What this means for reading errors**: a mismatched field list is reported as a mismatch between two `Cons`
chains, and the position where they diverge is the field that differs. An error mentioning
`Cons<u32, Cons<bool, Nil>>` where you expected three fields is telling you the third entry is missing.

<details>
<summary>Formal grammar</summary>

Both macros take a possibly-empty comma-separated list, in the Rust Reference's
[notation](https://doc.rust-lang.org/reference/notation.html):

```ebnf
ProductInput -> ( Type ( `,` Type )* `,`? )?

ProductExpr  -> ( Expression ( `,` Expression )* `,`? )?
```

`ProductInput` is the grammar of the type macro `Product!`, used in type position; `ProductExpr` is the
grammar of the value macro `product!`, used in expression position. `Type` and `Expression` are the Rust
grammar's productions. Both lists may be empty (`Product![]`, `product![]`) or carry a trailing comma, and
they line up positionally so a `product!` value has the type the corresponding `Product!` builds.

</details>

## Gotchas

**`Product!` and `product!` differ only in case, and the compiler's complaint will not say so.** Using the
type macro in expression position fails inside the macro's own parser, which is expecting a type, so the
message is a list of type-position tokens with no hint that the lowercase macro was wanted:

```text
error: expected one of: `for`, parentheses, `fn`, `unsafe`, `extern`, identifier, `::`, `<`, `dyn`,
       square brackets, `*`, `&`, `!`, `impl`, `_`, lifetime
```

**A one-element list is not a wrapper.** `Product![T]` is `Cons<T, Nil>`, which is a distinct type from `T`,
so a pipeline of one step still needs the list, and unwrapping it is a type error rather than a no-op.

**The empty list is `Nil`, a real value.** That is the difference from [`Sum!`](./sum.md), whose empty form is
the uninhabited `Void`. An empty record exists; an empty choice cannot.

**Element order is part of the type.** `Product![A, B]` and `Product![B, A]` are unrelated types. For a field
list this matters less than it sounds, because the entries are name-tagged
[`Field`](../types/field.md)s and the operations that consume them match on names. But for a handler pipeline
the order *is* the execution order.
